第6章 自顶向下语法分析

大家好，我是你们的讲师。上一章我们学习了语法分析的理论基础——上下文无关文法、推导、语法树、二义性。现在是时候把这些理论转化为实际运行的代码了。

自顶向下语法分析（Top-Down Parsing）是两种主流语法分析方法之一。它的核心思想很直观：从开始符号出发，尝试推导出输入的Token序列。如果推导成功，输入就是合法的；如果在某个步骤中没有产生式可用，输入就是不合法的。

你可以把它想象成"填空游戏"：你有一个句子模板（开始符号），你试着用产生式规则一步步展开，直到每个位置都填上具体的单词（Token）。如果在展开过程中发现当前展开方式导致无法匹配输入，就回溯换一种方式。当然，回溯是非常低效的——所以在工程实践中，我们会使用无需回溯的自顶向下分析方法，比如LL(1)。

本章结构：我们从最直观的递归下降解析器开始，然后深入理解FIRST集和FOLLOW集的理论基础，最后构建完整的LL(1)预测分析表。这个路径让你"先能动手写，再理解为什么这样写"。

递归下降解析器原理

递归下降解析（Recursive Descent Parsing）是最简单、最直观的手写语法分析方法。它的核心思想极其优雅：为文法的每个非终结符编写一个函数。函数的职责就是"匹配该非终结符所对应的Token序列"。

让我们看一个实际的例子。前面我们有过一个简单的表达式文法：

expr   → term ("+" term | "-" term)*
term   → factor ("*" factor | "/" factor)*
factor → NUM | "(" expr ")"

对应的递归下降解析器代码：

#include <stdio.h>
#include <stdlib.h>
#include <ctype.h>

/* ====== Token结构（来自词法分析器） ====== */
typedef enum {
    TOKEN_NUM, TOKEN_PLUS, TOKEN_MINUS,
    TOKEN_MUL, TOKEN_DIV, TOKEN_LPAREN,
    TOKEN_RPAREN, TOKEN_EOF, TOKEN_ERROR
} TokenType;

typedef struct {
    TokenType type;
    int int_value;      /* 仅当type为NUM时有效 */
    int line, column;
} Token;

/* ====== 解析器状态 ====== */
typedef struct {
    Token *tokens;      /* Token数组 */
    int pos;            /* 当前Token位置 */
    int length;         /* Token总数 */
} Parser;

/* 核心辅助函数 */
Token peek(Parser *p) {
    return p->tokens[p->pos];
}

Token consume(Parser *p) {
    return p->tokens[p->pos++];
}

int match(Parser *p, TokenType type) {
    if (peek(p).type == type) {
        consume(p);
        return 1;  /* 匹配成功 */
    }
    return 0;  /* 匹配失败 */
}

/* ====== AST节点（递归下降解析器的输出） ====== */
typedef struct ASTNode {
    char op;                /* '+', '-', '*', '/', 或 'N'（数字） */
    int int_value;          /* 仅当op为'N'时有效 */
    struct ASTNode *left;
    struct ASTNode *right;
} ASTNode;

ASTNode *make_num(int val) {
    ASTNode *n = malloc(sizeof(ASTNode));
    n->op = 'N';
    n->int_value = val;
    n->left = n->right = NULL;
    return n;
}

ASTNode *make_binop(char op, ASTNode *l, ASTNode *r) {
    ASTNode *n = malloc(sizeof(ASTNode));
    n->op = op;
    n->left = l;
    n->right = r;
    return n;
}

/* ====== 递归下降解析函数 ====== */

/* factor → NUM | "(" expr ")" */
ASTNode *parse_factor(Parser *p) {
    if (peek(p).type == TOKEN_NUM) {
        Token t = consume(p);
        return make_num(t.int_value);
    } else if (peek(p).type == TOKEN_LPAREN) {
        consume(p);  /* 吃掉 '(' */
        ASTNode *node = parse_expr(p);  /* 递归调用 */
        if (!match(p, TOKEN_RPAREN)) {
            fprintf(stderr, "错误: 期望 ')'\n");
            return NULL;
        }
        return node;
    } else {
        fprintf(stderr, "错误: 意外的Token类型 %d\n", peek(p).type);
        return NULL;
    }
}

/* term → factor ("*" factor | "/" factor)* */
ASTNode *parse_term(Parser *p) {
    ASTNode *left = parse_factor(p);
    if (!left) return NULL;

    while (peek(p).type == TOKEN_MUL || peek(p).type == TOKEN_DIV) {
        char op = (peek(p).type == TOKEN_MUL) ? '*' : '/';
        consume(p);
        ASTNode *right = parse_factor(p);
        if (!right) return NULL;
        left = make_binop(op, left, right);
    }
    return left;
}

/* expr → term ("+" term | "-" term)* */
ASTNode *parse_expr(Parser *p) {
    ASTNode *left = parse_term(p);
    if (!left) return NULL;

    while (peek(p).type == TOKEN_PLUS || peek(p).type == TOKEN_MINUS) {
        char op = (peek(p).type == TOKEN_PLUS) ? '+' : '-';
        consume(p);
        ASTNode *right = parse_term(p);
        if (!right) return NULL;
        left = make_binop(op, left, right);
    }
    return left;
}

/* 顶层入口：开始解析 */
ASTNode *parse(Parser *p) {
    p->pos = 0;
    ASTNode *ast = parse_expr(p);
    if (peek(p).type != TOKEN_EOF) {
        fprintf(stderr, "错误: 在解析完表达式后还有多余的Token\n");
        free(ast);
        return NULL;
    }
    return ast;
}

看到这个代码的关键模式了吗？parse_expr 调用 parse_term，parse_term 调用 parse_factor，而 parse_factor 在某些情况下又会调用 parse_expr——这形成了相互递归调用，正是"递归下降"这个名字的由来。

每个函数对应一个非终结符：这是递归下降解析最美的地方。当你查看一个语言的文法定义时，你几乎可以机械地将每条产生式转换为一个函数。每个非终结符变为一个函数名，每个选择（|）变为if-else分支，每个序列变为顺序调用。GCC和Clang等工业级编译器的解析器核心都是基于这种模式的（当然要复杂得多）。

FIRST集与FOLLOW集

递归下降解析器虽然直观，但有一个重要的问题：当 parse_expr 遇到一个Token时，它怎么知道应该选择哪个产生式？比如，如果当前Token是NUM，应该进入 term 分支；如果当前Token是 (，也应该进入 term 分支（因为括号内可以嵌套表达式）。

这个决策依赖两个关键的集合：FIRST集和FOLLOW集。

FIRST集

一个非终结符A的FIRST集是：从A出发，所有可能的推导结果中，第一个终结符（Token）的集合。

计算方法：

  • 如果A → aα（a是终结符），则a ∈ FIRST(A)。
  • 如果A → Bα（B是非终结符），则FIRST(B)中的所有元素都在FIRST(A)中。
  • 如果A → ε（空串），则ε ∈ FIRST(A)。

对于我们的表达式文法，计算FIRST集的示例：

  • FIRST(factor) = { NUM, ( }
  • FIRST(term) = FIRST(factor) = { NUM, ( }
  • FIRST(expr) = FIRST(term) = { NUM, ( }

FOLLOW集

一个非终结符A的FOLLOW集是：在所有的语法推导中，紧跟在A之后可能出现的第一个终结符的集合。

计算方法：

  • 将 $（输入结束符）加入 FOLLOW(开始符号)。
  • 如果有产生式 A → αBβ，则将 FIRST(β) - {ε} 加入FOLLOW(B)。
  • 如果有产生式 A → αB，或者 A → αBβ 且 ε ∈ FIRST(β)，则将 FOLLOW(A) 加入FOLLOW(B)。
非终结符 FIRST集 FOLLOW集
expr { NUM, ( } { $, ) }
term { NUM, ( } { $, ), +, - }
factor { NUM, ( } { $, ), +, -, *, / }
直观理解：FIRST集告诉解析器"当前非终结符能产生什么开头"——所以当看到NUM或(时，解析器知道"可以开始解析一个表达式了"。FOLLOW集告诉解析器"当前非终结符结束后，下一个Token应该是什么"——所以如果在一个表达式的末尾看到了 )，解析器知道"表达式结束，返回到上一层的括号"。这两个集合共同构建了解析器的决策逻辑。

LL(1)预测分析表

LL(1)是一种特殊的自顶向下语法分析方法。"LL"表示"从左到右扫描输入、最左推导"，"(1)"表示"每次只需要察看1个前瞻Token来做决策"。如果对于文法的任何状态和任何前瞻Token，都只有至多一个产生式可以选择，那么这个文法就是LL(1)文法。

构造预测分析表

预测分析表是一个二维表格：行为非终结符，列为终结符（包括$）。表格的每个单元格中存放的是"应该使用哪个产生式"。

构造算法：

  • 对于每条产生式 A → α：
  • 对于FIRST(α)中的每个终结符a（不包括ε），将 A → α 加入 M[A, a]。
  • 如果 ε ∈ FIRST(α)，则对于FOLLOW(A)中的每个终结符b（包括$），将 A → α 加入 M[A, b]。

如果表格中任何一个单元格出现了多个产生式，那么这个文法就不是LL(1)的——也就是说，它不能用一个前瞻Token确定性地做出决策。

下面是我们表达式文法的预测分析表：

// 预测分析表（简化的表示）
// 行 = 非终结符，列 = 前瞻Token

//            NUM      (        )      +      -      *      /      $
// expr       T→εT'    T→εT'    -      -      -      -      -      -
// term       F→εF'    F→εF'    -      -      -      -      -      -
// factor     NUM      (ε)      -      -      -      -      -      -
// (为简化，这里只展示了核心分发逻辑)

LL(1)分析算法的执行过程：

LL(1)分析算法伪代码：
1. 初始化栈 = [开始符号, $]
2. 输入指针指向第一个Token
3. 重复：
   a. 栈顶是X，当前输入Token是a
   b. 如果X == a == $ → 接受！解析成功。
   c. 如果X == a ≠ $ → 弹出X，输入指针前移。
   d. 如果X是非终结符：
       查表 M[X, a]
       如果为空 → 语法错误，报错
       如果非空 → 弹出X，将产生式的右部反向压入栈
   e. 否则 → 语法错误

左递归消除

递归下降解析器有一个重要的限制：它不能处理左递归文法。看这个例子：

expr → expr "+" term  | term

如果为这个产生式写递归下降函数：

void parse_expr() {
    parse_expr();  // 无限递归！！！
    match(TOKEN_PLUS);
    parse_term();
}

看到问题了吗？parse_expr 的第一件事就是调用自身——这是无限递归，必然导致栈溢出。

所以，所有用于自顶向下分析的文法必须消除左递归（Left Recursion）。

直接左递归消除

直接左递归的通用消除模式是：

// 原始（左递归）：
A → Aα | β

// 消除后（右递归）：
A  → β A'
A' → α A' | ε

应用到我们的表达式文法：

// 原始
expr → expr "+" term | term
term → term "*" factor | factor

// 消除后
expr  → term expr_tail
expr_tail → "+" term expr_tail | ε

term  → factor term_tail
term_tail → "*" factor term_tail | ε

消除左递归后的文法，就可以直接用递归下降解析器来处理了——expr_tail 函数在遇到 + 时递归调用自己，在遇到不属于 FIRST(expr_tail) 的Token时直接返回（ε产生式）。

一个常见的误解：很多人认为左递归消除了"="运算符的结合性就会变成右结合。其实不会——因为我们的AST构建方式可以让左递归文法（即使重写后）仍然保持左结合。关键在于：在解析 expr_tail 时，当遇到 +，我们构建的是 left = make_binop('+', left, right)，其中left是递归调用前的左子节点。只要我们在递归调用新建AST节点时将"当前节点"作为左子节点，结合性就是左结合的。如果你是右结合（比如赋值运算符 =），只需要反过来将当前节点作为右子节点即可。

一段真实的"踩坑"经历

我在第一次尝试用手写递归下降解析器解析一个复杂语言时，遇到了一个至今难忘的Bug。我想当然地把所有运算符都放在同一个优先级层级，并在函数中从左到右解析——但这样写出来的解析器对 a + b * c 的解析结果是 (a + b) * c 而不是期望的 a + (b * c)。

我当时花了一整天排查，一直以为是我的AST构建代码有问题。最后，一位同事看了一眼我的解析器代码说："你的 parse_expr 没有调用 parse_term，而是直接递归调用了 parse_expr——所以根本没有优先级层级。"

我恍然大悟。修正后的解析器把"加减法"和"乘除法"分成两个独立的函数，形成层级结构。正确的设计应该是：

// 乘法/除法在这一层处理（较高优先级）
parse_term() 被 parse_expr() 调用

// 加法/减法在这一层处理（较低优先级）
parse_expr() 调用 parse_term()

// 基础表达式（数字和括号）在最底层
parse_factor() 被 parse_term() 调用

这个层级结构就是优先级在解析器中的体现——调用层级越深的函数（如 parse_factor），其对应的运算符优先级越高。

经验法则：递归下降解析器中，优先级由调用层级表达。如果你的语言有N级优先级，你就需要N个嵌套的解析函数。每个函数处理一个优先级层级，并调用下一层级的函数来处理操作数。这个模式如此通用，以至于很多编译器教科书将其称为"优先级攀爬法（Precedence Climbing）"或"经典表达式解析模式"。

本章小结

本章我们全面学习了自顶向下语法分析的核心技术。我们从递归下降解析器入手——每个非终结符对应一个函数、相互调用形成递归结构——这是手写解析器最常用的模式。然后我们学习了FIRST集和FOLLOW集——这两个集合是构造预测分析表的基础。接着我们构造了LL(1)预测分析表和执行算法，理解了"用一个前瞻Token做出确定决策"的含义。最后，我们讨论了左递归消除——自顶向下解析器无法处理左递归文法，但可以通过特定的改写模式将左递归转换为右递归。

LL(1)的局限也很明显：很多实用语言并不是严格LL(1)的。比如C语言中，类型名和变量名的解析就需要额外的上下文信息（符号表）。这也是为什么工业级解析器常常在LL(1)基础上加入"回溯"或"语义信息"来扩展能力。

下一章，我们将转向自底向上的语法分析——LR系列方法。与自顶向下不同，自底向上分析器从输入Token出发，逐步"归约"（reduce）为越来越高的语法结构，直到归约到开始符号。LR分析器能处理的文法种类更广（不需要消除左递归），但构造也更复杂。让我们一起进入"移进-归约"的世界。
