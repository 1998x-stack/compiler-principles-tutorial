第23章 LLVM工具链实战

大家好，我是你们的讲师。在前面的章节中，我们深入探讨了 LLVM IR 的语法和语义，学习了如何将源代码转换为中间表示。但 LLVM 不仅仅是一个 IR 规范——它更是一整套工业级编译器工具链。如果你只在概念层面理解 LLVM，而没有亲手操作过它的工具，那就好比学会了游泳的理论却从未下过水。

这一章我们将卷起袖子，实地操作 LLVM 工具链中的每一个核心工具：clang（前端编译器）、opt（IR 优化器）、llc（目标代码生成器）、lli（IR 解释器/JIT 执行器），以及TableGen（领域特定代码生成器）。你还会学到如何开发自己的 LLVM Pass——这是 LLVM 生态中最强大的扩展机制之一。学完本章，你将能够像老手一样驾轻就熟地操作 LLVM 的每一条"生产线"。

Clang 工具链全景

Clang 是 LLVM 官方的 C/C++/Objective-C 前端，它不仅是一个编译器，更是一个完整的语言工具链。Clang 的设计哲学是"库化"——它的每个功能模块都以库的形式提供，可以被其他工具复用。因此，围绕着 Clang 衍生出了一系列强大的子工具。

clang -E：预处理

clang -E 只运行预处理阶段，输出展开后的源代码。这对于调试宏定义和头文件包含问题非常有用：

// 示例源文件：hello.c
#include <stdio.h>
#define GREETING "Hello, Compiler!"

int main() {
    printf("%s\n", GREETING);
    return 0;
}

运行 clang -E hello.c 会输出预处理后的结果——#include <stdio.h> 被替换为头文件的全部内容，GREETING 被展开为字符串字面量。输出通常有几百到上千行（取决于标准库头文件的大小）。配合 -C（保留注释）和 -P（去掉行标记）选项，可以更清晰地查看结果。

clang -fsyntax-only：语法检查

clang -fsyntax-only 执行词法分析、语法分析和语义分析，但不生成任何代码。这是最快的"我的代码有没有问题"检查方式，通常用于 IDE 的实时语法检查和 CI 的快速验证：

$ clang -fsyntax-only -Wall -Wextra hello.c
hello.c:7:14: warning: format specifies type 'int' but the argument has type 'long' [-Wformat]
    printf("%d\n", 42L);
             ~~      ^
             %ld

它提供的诊断信息比 GCC 更加清晰、易于理解——这也是 Clang 早年脱颖而出的关键优势之一。

clang-format：代码格式化

clang-format 是基于 Clang 的 AST 的代码格式化工具。与传统的基于正则表达式的格式化工具不同，它真正理解代码的结构，因此格式化结果更加可靠：

# 格式化单个文件（默认使用 LLVM 风格）
$ clang-format -i messy.c

# 使用 Google 风格
$ clang-format -i --style=Google messy.c

# 生成自定义配置文件
$ clang-format --style=LLVM --dump-config > .clang-format

.clang-format 文件可以纳入版本控制，这样团队中的每个人都使用相同的格式规范。常见的风格预设包括 LLVM、Google、Chromium、Mozilla、WebKit 等。

clang-tidy：静态分析

clang-tidy 是 Clang 生态中最受欢迎的静态分析工具。它基于 Clang 的 AST 运行一系列检查器（checker），发现代码中的潜在问题：

# 运行所有现代 C++ 相关的检查
$ clang-tidy -checks='modernize-*' source.cpp

# 检查并自动修复
$ clang-tidy -checks='modernize-use-auto' -fix source.cpp

# 常见的检查类别
# bugprone-*   : 容易出错的模式
# performance-*: 性能相关
# readability-*: 可读性建议
# cppcoreguidelines-*: C++ Core Guidelines 检查
小技巧：在实际项目中，建议将 clang-format 和 clang-tidy 集成到 pre-commit hook 中。这样每个 commit 都会自动格式化代码并运行静态分析，确保代码库始终保持一致的质量标准。

opt 与 Pass 管线

opt 是 LLVM 的IR 优化器，它是整个 LLVM 工具链中最强大的工具之一。它读取 LLVM IR（.ll 或 .bc 文件），在其上运行一系列的 Pass，然后输出优化后的 IR。理解 opt 的工作机制，是掌握 LLVM 优化管线的关键。

opt -passes=：指定优化管线

你可以用 -passes= 参数精确控制要运行的 Pass 序列：

# 运行标准的 -O2 优化管线
$ opt -passes=default<O2> input.ll -o output.bc

# 手动指定 Pass 序列
$ opt -passes=instcombine,gvn,simplifycfg input.ll -S -o output.ll

# 查看 IR 的 Pass 分析结果
$ opt -passes=print-callgraph input.ll -S 2>/dev/null

# 运行指定的分析 Pass 并打印结果
$ opt -passes=aa-eval input.ll -S -aa-eval-print 2>&1 | head -50

常用的 Pass 名称包括：

Pass 名称 类型 功能
instcombine Transformation 指令级别的代数化简和强度削弱
gvn Transformation 全局值编号，消除冗余计算
simplifycfg Transformation 简化控制流图，合并基本块
licm Transformation 循环不变式外提
dce Transformation 死代码消除
inline Transformation 函数内联
loop-vectorize Transformation 循环向量化
aa-eval Analysis 别名分析评估
domtree Analysis 构建支配树

PassManager：Pass 的管理框架

LLVM 的 Pass 管理框架经历了从 legacy PassManager 到 New Pass Manager (NPM) 的重大演进。NPM 是 LLVM 14 之后默认采用的架构，它解决了 legacy PM 的几个根本性问题：

  • 延迟计算：Pass 分析结果只在需要时才计算，避免不必要的开销
  • 显式依赖：Pass 之间通过 PreservedAnalyses 机制显式声明对分析结果的保留或失效
  • 线程安全：NPM 设计上考虑了多线程编译场景
  • 更清晰的 API：使用 llvm::FunctionPassManager、llvm::ModulePassManager 等类型明确的 Pass 管理器

Analysis vs Transformation Pass

LLVM 中有两大类型的 Pass：

Analysis Pass（分析型 Pass）不修改 IR，只收集信息。比如 DominatorTreeAnalysis 构建支配树信息，LoopAnalysis 识别循环结构。一个 Transformation Pass 可以通过 getResult<DominatorTreeAnalysis>(F) 来使用这些分析结果。

Transformation Pass（变换型 Pass）会修改 IR。比如 GVNPass 消除冗余计算、SimplifyCFGPass 简化控制流。Transformation Pass 在运行前会声明需要哪些分析结果，运行后通过 PreservedAnalyses 告知框架哪些分析仍然有效、哪些已失效需要重新计算。

核心设计思想：Analysis Pass 是"可缓存的只读信息"，Transformation Pass 是"消耗分析结果、生成新 IR"的消费者。这种分离使得 Pass 管线既灵活又高效——同一个分析结果可以被多个 Transformation Pass 共享，只有当 IR 被修改且影响该分析时才会触发重新计算。

自定义 LLVM Pass 开发

LLVM 最强大的特性之一就是它的可扩展性——你可以编写自己的 Pass 来执行自定义的变换或分析。无论你是想要实现一个专有的优化算法，还是在编译器层面做代码插桩，自定义 Pass 都是首选方案。

Pass 插件框架

LLVM 支持将 Pass 编译为共享库（.so），通过 opt -load-pass-plugin 动态加载，无需重新编译整个 LLVM：

// MyPass.cpp —— 一个简单的 FunctionPass
#include "llvm/IR/Function.h"
#include "llvm/IR/Instructions.h"
#include "llvm/Pass.h"
#include "llvm/Passes/PassBuilder.h"
#include "llvm/Passes/PassPlugin.h"
#include "llvm/Support/raw_ostream.h"

using namespace llvm;

namespace {

class MyFunctionPass : public PassInfoMixin<MyFunctionPass> {
public:
    PreservedAnalyses run(Function &F, FunctionAnalysisManager &AM) {
        errs() << "处理函数: " << F.getName() << "\n";

        for (auto &BB : F) {
            for (auto &I : BB) {
                // 统计指令数量
                errs() << "  指令: " << I.getOpcodeName() << "\n";
            }
        }

        // 没有修改 IR，所有分析结果都保留
        return PreservedAnalyses::all();
    }
};

} // anonymous namespace

// 注册 Pass 插件
extern "C" PassPluginLibraryInfo llvmGetPassPluginInfo() {
    return {
        LLVM_PLUGIN_API_VERSION,
        "MyFunctionPass",
        "0.1",
        [](PassBuilder &PB) {
            PB.registerPipelineParsingCallback(
                [](StringRef Name, FunctionPassManager &FPM,
                   ArrayRef<PassBuilder::PipelineElement>) {
                    if (Name == "my-function-pass") {
                        FPM.addPass(MyFunctionPass());
                        return true;
                    }
                    return false;
                });
        }
    };
}

编译和运行这个插件 Pass：

# 编译为共享库
$ clang++ -shared -fPIC -o MyPass.so MyPass.cpp \
    `llvm-config --cxxflags --ldflags --libs`

# 使用 opt 加载并运行
$ opt -load-pass-plugin=./MyPass.so \
      -passes=my-function-pass input.ll -S -o output.ll

ModulePass 与 FunctionPass

LLVM 支持不同粒度的 Pass：

  • ModulePass：作用在整个编译单元（Module）级别，可以访问所有全局变量和函数。适合进行全局优化，如符号重命名、全局变量合并。
  • FunctionPass：逐函数执行，每个函数独立处理。这是最常用的 Pass 类型，因为大多数优化都是函数本地的。
  • LoopPass：作用在每个循环上，用于循环优化。
  • CallGraphSCCPass：按调用图的强连通分量遍历，适合过程间分析。

LLVM Pass Builder

PassBuilder 是 New Pass Manager 中用于构建 Pass 管线的核心类。它提供了与 -O1、-O2、-O3、-Os 等优化级别对应的默认管线：

PassBuilder PB;
LoopAnalysisManager LAM;
FunctionAnalysisManager FAM;
CGSCCAnalysisManager CGAM;
ModuleAnalysisManager MAM;

// 注册所有分析 Pass
PB.registerModuleAnalyses(MAM);
PB.registerFunctionAnalyses(FAM);
PB.registerLoopAnalyses(LAM);
PB.registerCGSCCAnalyses(CGAM);
PB.crossRegisterProxies(LAM, FAM, CGAM, MAM);

// 构建 -O2 级别的 ModulePassManager
ModulePassManager MPM = PB.buildPerModuleDefaultPipeline(
    OptimizationLevel::O2);

// 运行 Pass 管线
MPM.run(Module, MAM);

如果你想在自定义的工具中嵌入 LLVM 优化管线，PassBuilder 是你需要熟悉的核心 API。它本质上是一个"工厂"——根据优化级别和用户指定的 Pass 名称字符串，自动构建出完整的 Pass 管线。

实战提醒：编写自定义 Pass 时，最容易被忽视的是 PreservedAnalyses 的正确设置。如果你的 Pass 修改了 IR 但没有正确标记哪些分析失效了，后续 Pass 可能基于过时的分析结果做出错误决策。这会导致非常难以调试的"无声"错误——代码仍能运行，但生成的代码可能有性能倒退甚至正确性问题。

TableGen 后端描述

TableGen 是 LLVM 中一个常被忽略但极其重要的组件。它是一种领域特定语言（DSL），用于描述目标架构的各种属性——指令格式、寄存器、调用约定等。然后 TableGen 工具会从这些描述中自动生成 C++ 代码，大大减少了编写后端的工作量。

指令定义（.td 文件）

以 RISC-V 架构为例，一个简单的指令定义示例如下：

// RISCVInstrInfo.td（简化版）
// 定义 RISC-V 的寄存器类
def GPR : RegisterClass<"RISCV", i32, 0,
    (add X0, X1, X2, X3, X4, X5, ...)>;

// 定义指令格式
class RVInst<dag outs, dag ins, string opcodestr, bits<32> opcode>
    : Instruction {
    let OutOperandList = outs;
    let InOperandList = ins;
    let AsmString = opcodestr;
    let Size = 4;  // 32位指令
}

// 定义具体的 ADD 指令
def ADD : RVInst<
    (outs GPR:$rd),      // 输出：目标寄存器
    (ins GPR:$rs1, GPR:$rs2),  // 输入：两个源寄存器
    "add $rd, $rs1, $rs2",     // 汇编字符串
    0x33>;                     // opcode

// 定义 ADDI（立即数加法）
def ADDI : RVInst<
    (outs GPR:$rd),
    (ins GPR:$rs1, i32imm:$imm12),
    "addi $rd, $rs1, $imm12",
    0x13>;

寄存器描述

寄存器描述定义了目标架构的所有寄存器及其属性：

// RISCVRegisterInfo.td（简化版）
// 定义寄存器类 GPR（通用寄存器）
def X0 : RISCVReg<0, "zero">;  // x0 永远是零
def X1 : RISCVReg<1, "ra">;    // 返回地址
def X2 : RISCVReg<2, "sp">;    // 栈指针

// 将这些寄存器组合成一个寄存器类
def GPR : RegisterClass<"RISCV", i32, 0,
    (add X0, X1, X2, X3, X4, X5, X6, X7, X8, X9, X10,
         X11, X12, X13, X14, X15, X16, X17, X18, X19,
         X20, X21, X22, X23, X24, X25, X26, X27, X28,
         X29, X30, X31)> {
    let RegInfos = RegisterInfo<32, 32>;  // 32个32位寄存器
}

指令选择模式

TableGen 还负责描述指令选择模式——即如何将 SelectionDAG 中的操作节点映射为目标指令。这部分通过 Pat 类来描述：

// 指令选择模式：将 DAG 节点映射为具体指令
// 将一个加法节点（add）和两个寄存器映射为 ADD 指令
def : Pat<
    (add GPR:$rs1, GPR:$rs2),
    (ADD GPR:$rs1, GPR:$rs2)
>;

// 将 add + imm 映射为 ADDI
def : Pat<
    (add GPR:$rs1, (i32 imm:$imm12)),
    (ADDI GPR:$rs1, imm:$imm12)
>;

// 将 load + GPR 映射为 LW 指令
def : Pat<
    (load GPR:$addr),
    (LW GPR:$addr, 0)
>;

从 TableGen 到 C++ 代码

写好了 .td 文件之后，用 llvm-tblgen 工具就能自动生成 C++ 代码：

# 从 .td 生成指令信息表
$ llvm-tblgen -gen-instr-info RISCV.td -o RISCVGenInstrInfo.inc

# 生成寄存器信息
$ llvm-tblgen -gen-register-info RISCV.td -o RISCVGenRegisterInfo.inc

# 生成指令选择器
$ llvm-tblgen -gen-dag-isel RISCV.td -o RISCVGenDAGISel.inc

# 生成汇编解析器
$ llvm-tblgen -gen-asm-parser RISCV.td -o RISCVGenAsmParser.inc

# 生成汇编打印器
$ llvm-tblgen -gen-asm-writer RISCV.td -o RISCVGenAsmWriter.inc

生成的 .inc 文件会被 #include 到后端的 C++ 源文件中。一个完整的 LLVM 后端可以生成数万行 C++ 代码，而开发者只需要维护几百行 .td 描述——这就是 TableGen 的威力所在。

理解 TableGen 的价值：如果没有 TableGen，为 LLVM 添加一个新的后端（比如一个新的 CPU 架构）将需要手动编写数万行高度重复的 C++ 代码——指令编码表、反汇编表、寄存器分配表等等。TableGen 将这种"声明式描述 → 命令式代码"的转换自动化了，使得 LLVM 能够快速支持数十种目标架构。目前 LLVM 支持的后端超过 30 个（x86、ARM、RISC-V、MIPS、PowerPC 等），每个后端的 .td 文件行数从几千到几万不等。

实战演练：完整的 Pass 开发流程

让我们把以上知识整合起来，完成一个实际的 Pass 开发流程。假设我们需要编写一个 FunctionPass，它能够统计并打印每个函数的循环嵌套深度：

// LoopDepthPass.cpp
#include "llvm/IR/Function.h"
#include "llvm/IR/LegacyPassManager.h"
#include "llvm/Pass.h"
#include "llvm/Passes/PassBuilder.h"
#include "llvm/Passes/PassPlugin.h"
#include "llvm/Analysis/LoopInfo.h"
#include "llvm/Support/raw_ostream.h"

using namespace llvm;

namespace {

struct LoopDepthPass : public FunctionPass {
    static char ID;
    LoopDepthPass() : FunctionPass(ID) {}

    bool runOnFunction(Function &F) override {
        // 获取 LoopInfo 分析结果
        LoopInfo &LI = getAnalysis<LoopInfoWrapperPass>().getLoopInfo();

        int maxDepth = 0;
        for (auto *L : LI) {
            int d = L->getLoopDepth();
            if (d > maxDepth) maxDepth = d;
        }

        errs() << "函数 " << F.getName()
               << " 的最大循环深度: " << maxDepth << "\n";
        return false;  // 不修改 IR
    }

    // 声明需要 LoopInfo 分析
    void getAnalysisUsage(AnalysisUsage &AU) const override {
        AU.addRequired<LoopInfoWrapperPass>();
        AU.setPreservesAll();
    }
};

} // anonymous namespace

char LoopDepthPass::ID = 0;

// 注册 Pass（legacy PM 方式）
static RegisterPass<LoopDepthPass> X(
    "loop-depth",
    "计算函数的循环嵌套深度",
    false,  // 不是 CFG 转换
    false   // 不是分析器
);

// 注册插件
extern "C" PassPluginLibraryInfo llvmGetPassPluginInfo() {
    return {
        LLVM_PLUGIN_API_VERSION,
        "LoopDepthPass",
        "1.0",
        [](PassBuilder &PB) {
            PB.registerPipelineParsingCallback(
                [](StringRef Name, FunctionPassManager &FPM,
                   ArrayRef<PassBuilder::PipelineElement>) {
                    if (Name == "loop-depth") {
                        FPM.addPass(LoopDepthPass());
                        return true;
                    }
                    return false;
                });
        }
    };
}

开发自定义 Pass 时的典型工作流：

  1. 编写 Pass 的 C++ 代码，继承自 PassInfoMixin（新 PM）或 FunctionPass（旧 PM）
  2. 编译为共享库（.so）
  3. 使用 opt -load-pass-plugin 加载并测试
  4. 通过 llvm-lit（LLVM 集成测试框架）编写测试用例
  5. 确认结果正确后，将 Pass 添加到正式的优化管线中

llc 与 lli：代码生成与即时执行

llc 是 LLVM 的静态代码生成器，它将 IR 转换为目标平台的汇编代码：

# 生成 x86 汇编
$ llc input.ll -o input.s

# 生成 ARM 汇编（交叉编译）
$ llc -march=arm input.ll -o input-arm.s

# 输出 LLVM 的 instruction selection 调试信息
$ llc -debug-only=isel input.ll -o input.s 2>&1 | head -50

# 查看生成的机器指令（MI 格式）
$ llc -print-machineinstrs input.ll -o /dev/null 2>&1

lli 是 LLVM 的IR 解释器/JIT 执行器，它可以直接执行 .ll 或 .bc 文件，无需编译为机器码：

# 直接运行 LLVM IR
$ lli input.ll

# 启用 JIT 编译（默认）
$ lli -jit-kind=orc input.ll

# 使用解释模式（不 JIT）
$ lli -force-interpreter input.ll

lli 特别适合在开发调试阶段快速验证 IR 的正确性——你不需要经过完整的汇编-链接过程就能运行代码。
