第13章 代码生成

大家好，我是你们的讲师。经过漫长的前端之旅——词法分析、语法分析、语义分析、IR 生成与优化——我们终于走到了编译器旅途的终点：代码生成（Code Generation）。这是编译器最激动人心的阶段：把抽象的、与机器无关的中间表示，最终翻译为具体 CPU 能够执行的目标机器指令。

这是一个从"无限可能性"到"有限约束"的过程。IR 中的一条 add 指令，在 x86-64 上可能有十余种不同的编码方式（使用哪些寄存器、寻址模式如何、操作数大小等）。代码生成器需要从这些可能性中选出最优的组合——既要保证正确性，又要追求性能，还要兼顾代码大小。这不仅是计算机科学，也是一门手艺活。

代码生成的挑战：与 IR 的"理想世界"不同，真实 CPU 有一大堆约束——寄存器数量有限（x86-64 通用寄存器仅 16 个）、指令有固定的操作数格式（不能随便选三个寄存器）、某些指令有延迟和吞吐量差异。代码生成器必须在这些约束下做出最优的取舍。一个高质量的代码生成器，能让同一份 IR 生成的代码性能差距达到 2-5 倍。

代码生成概述

代码生成的过程可以分解为三个主要子任务：

  • 指令选择（Instruction Selection）：将 IR 指令映射为目标架构的具体指令。比如 IR 中的 add i32 %a, %b 映射为 x86-64 的 ADD EAX, EBX。
  • 寄存器分配（Register Allocation）：将 IR 中的虚拟寄存器（无限多个）映射到物理寄存器（有限多个）。当物理寄存器不够用时，需要溢出（spill）到内存。
  • 指令调度（Instruction Scheduling）：重新排列指令顺序，以充分利用 CPU 的流水线，减少流水线停顿。现代 CPU 可以同时执行多条指令（超标量），指令调度决定了这种并行性能否被充分利用。

这三个任务还有相互依赖关系：指令选择影响寄存器分配（不同的指令使用不同的寄存器），寄存器分配影响指令调度（溢出到内存的 load/store 指令增加延迟）。现代编译器通常先做指令选择，再做寄存器分配，最后做指令调度，然后通过多次迭代来优化。

Maximal Munch 指令选择

Maximal Munch 是一种经典的指令选择算法，属于树覆蓋（Tree Covering）方法的一种变体。它的核心思想简单而直观：

在 IR 的树形表示（或 DAG 表示）中，每次选择尽可能大的子树来匹配一条目标指令。从树根开始，找到能覆盖当前节点的最大指令模板，匹配并发射指令，然后递归处理剩余的子节点。

用人话说就是："能一条指令搞定的事情，绝不用两条"。比如在 x86-64 上，a = a + 1 对应的 IR 可以用两条指令实现：

; IR 形式
t1 = add a, 1
a = t1

; 两条汇编指令
MOV EAX, [a]
ADD EAX, 1

; 但 x86-64 有一条 INC 指令可以"一口吃掉"整个操作：
INC DWORD [a]  ; 一条指令完成 "a += 1" 的全部功能

Maximal Munch 算法会优先匹配 INC DWORD [a] 这个大模板，而不是拆成 MOV + ADD 两个小模板。

算法实现

// Maximal Munch 指令选择的简化实现
class InstructionSelector {
    // 指令模板库：每个模板包含匹配模式和生成代码
    List<InstructionTemplate> templates;

    // 对一棵表达式树进行指令选择
    void select(ExprNode root, List<Instruction> output) {
        // 1. 尝试匹配所有指令模板
        // 2. 选择匹配节点数最多的模板（"最大一口"）
        // 3. 为该模板生成指令，加入输出列表
        // 4. 递归处理剩余的子树

        InstructionTemplate best = null;
        int bestSize = 0;

        for (InstructionTemplate tmpl : templates) {
            MatchResult result = tmpl.tryMatch(root);
            if (result != null && result.matchedNodes > bestSize) {
                best = tmpl;
                bestSize = result.matchedNodes;
            }
        }

        if (best == null) {
            throw new CodeGenError("无法匹配指令: " + root);
        }

        // 对子节点递归选择
        for (ExprNode child : best.getOperands(root)) {
            select(child, output);
        }

        // 发射当前指令
        output.add(best.emit(root));
    }
}
指令模板 匹配的 IR 模式 生成代码 代价（周期数）
INC add X, 1 → X INC X 1
ADD 寄存器 add X, Y → Z ADD Z, X, Y 1
ADD 内存 add X, [addr] → Z ADD Z, [addr] 2
LEA add a, mul b, c → d LEA D, [A + B*C] 1
MOV + ADD add X, Y → Z（默认回退） MOV Z, X; ADD Z, Y 2
LEA 指令的神奇之处：x86 的 LEA（Load Effective Address） 指令本意是计算内存地址，但它实际上可以执行 reg = base + index*scale + offset 这种运算，而且不访问内存、不修改标志位。聪明的编译器会用 LEA 来优化简单的算术组合。比如 t1 = a * 5 可能被优化为 LEA EAX, [EAX + EAX*4]（EAX*4 + EAX = EAX*5）。一条 LEA 指令完成了乘法和加法，代价仅 1 个时钟周期——这比用 IMUL 乘法指令快得多。

图着色寄存器分配

寄存器分配是代码生成中最具挑战性的子问题之一。LLVM IR 可以有无穷多个虚拟寄存器（如 %t1, %t2, ...），但真实 CPU 的物理寄存器非常有限（x86-64 通用寄存器仅 16 个，ARM64 有 31 个）。

图着色（Graph Coloring）寄存器分配是最经典的寄存器分配算法，它将分配问题转化为一个图着色问题：

算法步骤

  1. 活性分析（Live Analysis）：确定每个虚拟寄存器在哪些程序点上是"活跃的"（即它的值在后续还会被使用）。
  2. 构建冲突图（Interference Graph）：如果两个虚拟寄存器在同一程序点上活跃，它们之间存在冲突，在图中连一条边。冲突的寄存器不能分配到同一个物理寄存器。
  3. K 着色（K-Coloring）：用 K 种颜色（K = 物理寄存器数量）对冲突图进行着色。如果着色成功，每种颜色对应一个物理寄存器。
  4. 溢出处理（Spilling）：如果着色失败（需要更多颜色），选择某些虚拟寄存器溢出到内存——即它们不占用寄存器，而是通过栈上的 alloca 来存储。
// 冲突图构建的简化示意
//
// 源代码:                       活性区间:
// t1 = a + b                    t1: [1-3]
// t2 = t1 * c   ------\         t2: [2-4]
// t3 = t1 + d         |         t3: [3-5]  (不活性)
// t4 = t2 * t3  -----/          t4: [4-6]
//
// 冲突图:
//   t1 --- t2  (在行 2 同时活跃)
//   t1 --- t3  (在行 3 同时活跃)
//   t2 --- t3  (在行 4 同时活跃)
//   t2 --- t4  (在行 4-5 同时活跃)
//   t3 --- t4  (在行 4-5 同时活跃)
//
// 如果有 2 个物理寄存器 (RAX, RBX):
//   着色结果: t1=RAX, t2=RBX (冲突，不同色)
//            t3=RAX (t3 与 t1 不冲突，可复用 RAX)
//            t4=RBX (t4 与 t2 不冲突，可复用 RBX)
// 成功！只需要 2 个物理寄存器就完成了分配。
溢出开销：寄存器溢出一旦发生，性能代价是巨大的。每次溢出变量的读取和写入都需要额外的 load 和 store 指令访问内存。对于循环体内的溢出变量，这个代价尤其严重。因此寄存器分配器会优先溢出那些"使用频率最低"或"活性区间最长"的变量。现代编译器（如 LLVM 的 greedy register allocator）还会根据溢出代价估算进行更智能的决策，甚至主动将某些变量放在内存中（如果它们的计算代价低于溢出代价）。

窥孔优化

窥孔优化是代码生成阶段的"最后一公里"优化。与前端的全局优化不同，窥孔优化只关注一个滑动窗口中的少数几条连续指令，寻找可以被替换或消除的局部模式。它的名字来源于"透过一个小孔（peephole）观察指令序列"这个形象比喻。

常见的窥孔优化规则

以下是一些经典的窥孔优化模式（左边是优化前的指令序列，右边是优化后的等价替换）：

// 规则1: 冗余加载消除
MOV EAX, [mem]        // 如果 CPU 刚执行过 store，
MOV [mem], EBX    →   // 而且 EAX 的值来自 mem，
                      // 可以消除第一个 MOV
// 实际上更常见的是:
STORE [addr], EAX     // 写入一个地址
LOAD EAX, [addr]  →   // 又立刻读回来 — 消除此条 load
// 因为 EAX 中已经是最新的值了

// 规则2: 常量折叠 (汇编层面)
MOV EAX, 0
ADD EAX, 5        →   MOV EAX, 5

// 规则3: 冗余跳转消除
JMP L1             →
L1: JMP L2    →    JMP L2
// 直接跳转到最终目标，缩短控制流链

// 规则4: 无用代码消除
MOV EAX, EBX
...                 →   (删除第一条 MOV)
// 如果 EBX 的值在此处不再需要，且 EAX 被覆盖

// 规则5: 强度削弱
MOV EAX, X          →   MOV EAX, X
IMUL EAX, 3             ADD EAX, X     // 3*X = X*2 + X = X+X+X 有问题？
                              SHL EAX, 1   // 实际上是 LEA 更优
// 用移位+加法代替整数乘法（乘法指令通常较慢）
窥孔优化的威力：单个窥孔规则的效果往往很小——可能只消除一条指令。但几十条窥孔规则组合起来，在大型代码库上运行时，效果非常显著。GCC 和 LLVM 中都有数百条窥孔规则，每个规则针对一种特定的局部模式。由于窥孔优化的作用范围小（通常 3-5 条指令），它非常快，可以多次迭代运行——每次迭代可能打开新的优化机会。这也是为什么编译器的 -O2 级别通常包含多轮窥孔优化。

本章小结

本章我们学习了代码生成阶段的三个核心任务。指令选择负责将 IR 指令映射为目标机器指令，其中 Maximal Munch 算法通过"最大一口"策略来优先选择最强大的指令模板。寄存器分配通过图着色的方法，将无限多的虚拟寄存器映射到有限的物理寄存器上，当物理寄存器不够时通过溢出到内存来处理。最后，窥孔优化在生成的指令序列上做局部优化，消除冗余、简化模式。

至此，我们已经走完了编译器从源代码到机器代码的完整旅程。但故事还没有结束——生成的代码还需要在一个运行时系统中正确执行。下一章，我们将讨论运行时系统的重要概念：栈帧布局、调用约定、垃圾回收、以及异常处理机制。这些知识不仅对编译器开发者有意义，对每一个系统程序员来说都至关重要。敬请期待。
