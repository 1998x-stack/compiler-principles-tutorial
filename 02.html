第2章 编译器的历史演进

大家好，我是你们的讲师。上一章我们了解了编译器是什么、它包含哪些阶段。但在开始深入技术细节之前，我觉得有一件事非常重要——理解这些技术从何而来。

编译器不是某个人某天一拍脑袋发明的东西。它经历了近七十年的演进，从1950年代IBM实验室里那个"不可能完成的任务"，到今天驱动着整个世界软件工业的LLVM生态。这段历史充满了天才的灵光一现、孤注一掷的创业故事、以及开源社区改变世界的壮举。了解这段历史，你会对编译器产生更大的敬意，也会理解它为什么被设计成今天这个样子。

本章导航：我们将沿着时间线，从最早的FORTRAN编译器开始，经历GCC的崛起与自由软件运动，再到LLVM对编译器架构的彻底重构，最后俯瞰今天百花齐放的编译器生态。这是一段关于"如何让机器理解人类"的六十年征程。

早期编译器时代（1950s-60s）

在计算机诞生的最初十几年里，所有人都是用机器码或汇编语言编程的。每一个指令都要手动编写，每一个内存地址都要亲自管理。你可以想象一下——如果你想写一个简单的循环，你得自己计算跳转指令的目标地址，一旦中间插入一行代码，后面的所有地址都要重新计算。这在今天是不可想象的。

就在这样的背景下，一个大胆的想法诞生了："能不能让计算机自己把自己翻译成机器码？"

第一个FORTRAN编译器（1957）

1953年，IBM的John Backus向他的领导提交了一份提案——设计一种"更像数学表达式"的编程语言，并开发一个程序把它自动翻译成机器码。当时几乎所有人都觉得这是天方夜谭。计算机本身就是个新生事物，让计算机自动完成编程？这听起来像是在说"让炉子自己做饭"。

但Backus得到了IBM的支持。从1954年到1957年，他的团队在IBM 704计算机上开发了第一个FORTRAN编译器。这个项目在当时被认为风险极高——团队只有十几个人，却要用机器码为一个刚刚问世的机器编写一个前所未有的复杂程序。

1957年4月，第一个FORTRAN编译器交付使用。结果震惊了所有人：用FORTRAN编写的程序，编译后的机器码执行效率只比手写汇编慢不到20%，而开发效率提升了数倍。当时一份报告这样评价："FORTRAN编译器在优化方面做得如此出色，以至于许多程序员宁愿用FORTRAN也不愿手写汇编。"

冷知识：FORTRAN编译器中已经包含了许多今天看来仍然先进的优化技术——常量折叠、寄存器分配、循环展开等。Backus团队在没有任何前人经验可参考的情况下，从零创造了这些技术。他们是真的"摸着石头过河"，而且摸得非常好。

Backus-Naur范式的诞生

FORTRAN的成功催生了更多高级语言。ALGOL 60的出现带来了一个重要的副产品——Backus-Naur Form (BNF)，一种描述编程语言语法的形式化符号系统。Backus和丹麦计算机科学家Peter Naur共同提出了这一范式，它至今仍是描述语法的标准工具。

BNF的重要性怎么强调都不为过。在BNF出现之前，编程语言的语法是用自然语言描述的，充满了歧义和模糊之处。BNF让语法描述变得精确、简洁，更重要的是——它让语法分析的自动化成为可能。

这一时期的其他里程碑还包括：

年份 事件 意义
1957 FORTRAN编译器 第一个完整的编译器，证明了高级语言编译的可行性
1958 LISP解释器 John McCarthy发明LISP，带来了垃圾回收等概念
1960 ALGOL 60 + BNF 形式化语法描述的开端，影响了几乎所有后续语言
1962 COBOL编译器 面向商业应用，推动了编译器在非科学计算领域的应用
1969 Ken Thompson实现B语言 为C语言的诞生奠定了基础

GCC与自由软件运动

从1960年代到1980年代，编译器商业化的趋势非常明显。各大硬件厂商都提供自己平台的专有编译器，价格昂贵且源代码保密。如果你用DEC的机器，你就只能用DEC的编译器；如果你换到Sun的机器，你得重新买一套编译器。这导致了一个严重的问题——软件不可移植。

Richard Stallman与GNU项目

1983年，在MIT人工智能实验室工作的Richard Stallman发表了GNU宣言，宣布启动GNU项目（GNU's Not Unix），目标是创建一个完全自由、开源的操作系统。而操作系统的基石之一，就是一个高质量的C语言编译器。

1985年，Stallman基于Pastel编译器的部分代码，开始了GCC（GNU C Compiler）的开发。他采用了三段式架构——前端（解析C语言）、中间端（与语言无关的优化）、后端（生成目标机器码）——这使得GCC可以轻松支持新的语言和新的目标平台。

GCC的核心创新：三段式架构让编译器不再是一个语言-平台紧密耦合的"黑盒"。只需要实现一个新的前端，任何语言都可以享受GCC的所有优化和后端支持；只需要实现一个新的后端，GCC就可以在所有架构上编译所有支持的语言。这种"一次编写，随处编译"的理念，是GCC迅速崛起的关键。

GCC 1.0与它的崛起

1987年，Stallman发布了GCC 1.0。虽然最初版本只支持C语言，支持的平台也只有VAX和Sun 3，但它展现出的潜力让整个社区为之振奋。最重要的是——它是自由的。用户可以查看源码、修改它、为它贡献新的功能。

GCC的崛起速度惊人。到1990年代初，GCC已经支持了几乎所有的Unix-like平台和十多种编程语言的前端（包括C++、Objective-C、Fortran、Java等）。Linux内核从诞生起就使用GCC编译。可以毫不夸张地说，没有GCC，就没有Linux，就没有今天开源世界的繁荣。

当然，GCC也不是完美的。它的代码库在长期发展后变得非常复杂——毕竟它是在1980年代设计的架构。代码高度耦合，添加新的优化pass变得困难，而且GCC使用了递归下降解析器配合手工编写的词法分析器，使得代码难以维护。这些问题为后来者留下了机会。

一个有趣的对比：Stallman在开发GCC时，GNU项目的创始人协议要求所有贡献者将版权转让给自由软件基金会（FSF）。这一方面保护了GPL许可证的有效性，另一方面也让许多企业（包括苹果、Google）望而却步——他们不愿意将代码版权交给FSF。这间接催生了LLVM和Clang的诞生。

LLVM革命

时间来到2000年，一位名叫Chris Lattner的UIUC博士生正在研究一个"如何在整个程序生命周期中保持编译优化信息"的问题。他的博士论文课题演变成了一个叫做LLVM（Low Level Virtual Machine）的项目——这个名字后来被重新解释为"LLVM is not a Virtual Machine"。

LLVM的核心哲学

LLVM与GCC最本质的区别在于：LLVM设计了一个第一公民的中间表示（IR）。所有前端（Clang、rustc、Swiftc等）都生成LLVM IR，所有优化都在LLVM IR上进行，所有后端都将LLVM IR翻译为目标代码。这种设计带来了几个至关重要的优势：

  • 模块化：编译器被拆分为独立的库，每个优化是一个pass，可以独立开发、测试、组合。
  • 可复用性：你不需要写一个完整的编译器——你可以复用LLVM的优化管线，只需要写你自己的前端和（如果需要）后端。
  • JIT友好：LLVM IR天然适合即时编译，因为你可以保留IR的语义信息，在运行时根据profile数据重新优化。
  • 链接时优化（LTO）：LLVM可以在链接时跨编译单元进行全局优化，这是传统编译器做不到的。
# LLVM的三段式架构示意

# 1. 前端（Frontend）: 源代码 → AST → LLVM IR
#    Clang (C/C++/ObjC)     → LLVM IR
#    rustc (Rust)           → LLVM IR
#    swiftc (Swift)         → LLVM IR

# 2. 优化器（Optimizer）: LLVM IR → 优化后的 LLVM IR
#    opt 工具使用一系列 pass 进行优化：
#    - mem2reg (将内存操作提升为SSA寄存器)
#    - gvn (全局值编号)
#    - inline (函数内联)
#    - loop-rotate (循环旋转)
#    ...

# 3. 后端（Backend）: LLVM IR → 目标机器码
#    llc 工具生成：
#    - x86_64 机器码
#    - ARM64 机器码
#    - RISC-V 机器码
#    - WebAssembly
#    ...

Chris Lattner的博士论文（2004）

2004年，Lattner完成了他的博士论文"LLVM: An Infrastructure for Multi-Stage Optimization"。这篇论文不仅仅是一个学位要求——它提出了一种全新的编译器设计思想。论文的核心观点是：优化应该在整个程序生命周期中进行，包括编译时、链接时、安装时、运行时。为了实现这一点，LLVM IR被设计为一种持久的、携带丰富类型信息的、与机器无关的表现形式。

毕业后，Lattner加入了苹果公司。苹果当时正面临一个棘手的困境——他们深度依赖GCC，但GCC的版权条款（GPLv3）和FSF的版权转让政策与苹果的商业策略严重冲突。苹果需要一个替代方案。

2007年，苹果发布了Clang——一个基于LLVM的C/C++/Objective-C编译器前端。Clang相比GCC有显著优势：编译速度快（快2-3倍）、错误信息友好（告诉你错误在哪一行的第几个字符，而不是模糊地"这里出错了"）、代码库更小更清晰。到2012年，苹果在macOS上彻底用Clang替换了GCC。

LLVM Monorepo生态

今天的LLVM采用Monorepo策略——所有子项目（LLVM核心、Clang、LLD链接器、libc++标准库、compiler-rt、MLIR等）都在同一个代码仓库中管理。这种策略保证了各组件的版本一致性，降低了贡献门槛。

LLVM的社区规模之大令人惊叹：截至2024年，LLVM项目有超过3000名活跃贡献者，代码量超过500万行。每年有两次大型发布（3月和9月），每次发布都包含数千个commit。

特征 GCC LLVM/Clang
许可证 GPLv3 Apache 2.0 + BSD
架构 三段式，但各组件耦合较紧 高度模块化的库架构
IR设计 GIMPLE/RTL（内部表示，非一等公民） LLVM IR（一等公民，序列化到文件）
编译速度 较慢 快（约2-3倍于GCC）
错误信息 不够精确 非常清晰友好
JIT支持 无原生JIT 基于MCJIT/ORC的原生支持

现代编译器生态

今天，编译器领域的版图已经非常清晰。LLVM生态经历了近20年的发展，已成为编译器基础设施的事实标准。让我们看看在LLVM之上建立的语言有多少：

  • Rust（rustc）：Mozilla开发的系统编程语言，使用LLVM作为后端。Rust的所有权系统和借用检查器是语言的亮点，而LLVM保证了生成的代码性能与C/C++相当。
  • Swift：苹果开发的语言，Swift编译器（swiftc）使用LLVM作为后端。Swift的编译管线中还有一个独特的SIL（Swift Intermediate Language）层。
  • Julia：科学计算语言，其JIT编译器基于LLVM实现。Julia的LLVM调用非常直接——它甚至允许用户在运行时生成IR并调用LLVM优化管线。
  • Zig：现代系统编程语言，自带的编译器也基于LLVM实现，提供了编译时执行（comptime）等独特特性。
  • Crystal：语法类似Ruby但编译执行的编程语言，同样基于LLVM。

当然，GCC也没有被淘汰。它仍然是Linux发行版的默认编译器，在嵌入式系统领域也有大量用户。GCC在某些架构和特定类型的代码上仍能生成比LLVM略优的代码。两者的竞争关系实际上推动了整个编译器技术的进步。

行业趋势：如果你今天要设计一种新的编程语言，LLVM几乎是默认选择。你只需要实现一个生成LLVM IR的前端，就能免费获得跨平台支持、20年积累的优化pass、以及活跃的社区支持。这就是"基础设施"的力量——LLVM降低了创建新语言的进入门槛，这解释了为什么2010年代以来出现了如此多的新编程语言。

一段真实的"踩坑"经历

我来讲一个编译器历史带来的实际问题。有一次，我在将一段C++代码从GCC移植到Clang编译时，发现程序在特定的输入下产生了不同的结果。排查了一天，最终发现问题出在浮点运算的严格性上。

GCC默认使用 -ffast-math 的保守版本，而Clang在某些优化级别下会进行更激进的浮点数重排。我们的代码中有一段计算 a * b + c 的表达式，在GCC下被编译为FMA（融合乘加）指令使用完整的中间精度，而在Clang下被拆分为两次操作。因为浮点运算没有结合律，(a * b) + c 和 FMA a * b + c 的结果在尾数上会有微小差异。

这个差异在单次计算中微不足道，但我们的算法要迭代几百万次——误差累积后导致了不同的结果。解决方案很简单：加上 -ffp-contract=on 让Clang的行为与GCC一致。但如果我不了解两家编译器的历史渊源和设计哲学的差异，这个问题可能会排查数周。

教训：GCC和LLVM虽然目标相同（把高级语言翻译成正确的机器码），但它们在优化策略、实现细节、默认行为上有大量差异。当你在不同编译器之间迁移代码时，永远不要假设"同一个C++代码在不同编译器下行为一致"。编译器历史的知识让你理解这些差异的根源，而不是在黑暗中摸索。

本章小结

这一章我们追溯了编译器近七十年的发展历程：从1957年Backus团队在IBM 704上创造第一个FORTRAN编译器，到Stallman以一己之力启动GCC项目并点燃了自由软件运动，再到Chris Lattner的博士论文催生了LLVM——这个重新定义了编译器基础设施的现代化框架。

这段历史告诉我们一个重要的道理：编译器不仅仅是"技术"，它也是"文化"和"社区"的产物。GCC是开源精神的象征，LLVM是工程模块化的典范。理解这些背景，你就能更好地理解为什么编译器被设计成今天这个样子——为什么LLVM IR要设计成"一等公民"？因为Lattner在论文中论证了跨阶段优化的必要性。为什么GCC的代码库如此难以贡献？因为它诞生于1980年代，背负了沉重的历史包袱。
