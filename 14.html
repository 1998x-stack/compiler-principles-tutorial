第14章 运行时系统

大家好，我是你们的讲师。经过前面的章节，我们已经知道编译器如何将源代码翻译为目标机器的指令。但这些指令被加载到内存后，是如何组织、协调、管理的呢？当你的程序调用一个函数，call 指令的背后发生了什么？局部变量存在哪里？堆上的内存谁负责回收？抛出异常时 CPU 怎么知道跳到哪去执行？

这些问题的答案，构成了运行时系统（Runtime System）的范畴。运行时系统是编译器生成的代码与操作系统之间的一层"软性基础设施"——它不是编译器的某个阶段，而是编译器在生成代码时需要遵守的一系列约定和插入的一整套辅助机制。栈帧布局、调用约定、内存管理、异常处理——这些都是运行时系统的核心组成部分。

为什么要关心运行时系统？即使你从不需要实现编译器，理解运行时系统也是写出高性能代码的关键。栈溢出是怎么发生的？为什么递归太深会 crash？虚函数调用的性能代价来自哪里？为什么某些语言有 GC 而另一些没有？这些问题表面上"语言特性"，本质上都是运行时系统的设计决策。掌握这些知识，你会成为一名真正的系统级程序员。

栈与栈帧

函数调用是程序执行的基本单位。每次函数调用，运行时系统都会在调用栈（Call Stack）上分配一个新的栈帧（Stack Frame），用于存储该函数的局部变量、参数、返回地址等信息。

栈帧布局

一个典型的栈帧结构如下（以 x86-64 System V ABI 为例）：

高地址
      +------------------+
      | 调用者的栈帧     |
      +------------------+
      | 第 7 个及以后的  | ← 超出寄存器传参范围的参数
      | 参数（如果有）    |
      +------------------+
      | 返回地址         | ← call 指令自动压入
      +------------------+
      | 保存的 %rbp      | ← 旧帧指针（push rbp）
      +------------------+ ← %rbp (帧指针)
      | 局部变量区域     |
      | (由 alloca 分配)  |
      +------------------+
      | 寄存器溢出区域    |
      | (callee-saved)   |
      +------------------+
      | 临时量           |
      +------------------+ ← %rsp (栈指针)
低地址

Prologue 与 Epilogue

每个函数调用的开始和结束，编译器会插入特殊的代码序列——prologue（序言）和 epilogue（尾声）：

; 一个函数的典型 prologue 和 epilogue (x86-64)
my_function:
    ; === prologue 开始 ===
    push    rbp           ; 保存调用者的帧指针
    mov     rbp, rsp      ; 设置当前函数的帧指针
    sub     rsp, 32       ; 为局部变量分配 32 字节栈空间
    ; === prologue 结束 ===

    ; ... 函数体代码 ...

    ; === epilogue 开始 ===
    mov     rsp, rbp      ; 恢复栈指针（释放局部变量空间）
    pop     rbp           ; 恢复调用者的帧指针
    ret                   ; 返回（弹出返回地址并跳转）
    ; === epilogue 结束 ===

帧指针 vs 栈指针

在上面的代码中，rbp（基址指针/帧指针）和 rsp（栈指针）是两个关键的寄存器：

  • %rbp（帧指针）：在整个函数执行过程中保持不变，指向当前栈帧的固定位置。所有局部变量和参数都通过这个指针的偏移量访问（如 [rbp - 4] 表示第一个局部变量）。
  • %rsp（栈指针）：随着 push/pop、call/ret 和栈空间的分配/释放而不断变化。在函数的 prologue 之后，编译器通过 sub rsp, N 一次性分配好所有局部变量空间，此后函数体内一般不再修改 rsp。
优化技巧：在启用优化（如 -O2）时，编译器通常会省略帧指针——因为所有局部变量可以通过栈指针的偏移量直接访问。这样做的好处是：释放出了一个通用寄存器（%rbp）供其他用途使用，并且减少了 prologue/epilogue 中的 push/pop 指令数量。代价是调试体验下降——栈回溯（stack unwinding）变得困难。GCC 和 Clang 使用 -fomit-frame-pointer 来控制此行为。

调用约定

当一个函数调用另一个函数时，双方必须就以下问题达成一致：参数怎么传递？返回值放哪里？哪些寄存器可以被被调用者随意修改？哪些寄存器必须由被调用者保存？这些约定就是调用约定（Calling Convention）。

如果两个函数是用不同调用约定编译的，它们之间的函数调用就会出错——参数可能被放在了错误的地方，或者寄存器的值被意外破坏。

常见的调用约定

约定名称 平台 参数传递 寄存器保存 栈清理
cdecl x86-32 (Windows, Linux) 全部通过栈传递（从右到左压栈） EAX, ECX, EDX 是 caller-saved 调用者清理栈
stdcall x86-32 (Win32 API) 全部通过栈传递（从右到左压栈） 同 cdecl 被调用者清理栈
fastcall x86-32 头两个参数通过 ECX, EDX 传递，其余在栈上 同 cdecl 被调用者清理栈
System V AMD64 x86-64 (Linux, macOS, BSD) 前 6 个整数参数通过 RDI, RSI, RDX, RCX, R8, R9 传递；浮点参数通过 XMM0-XMM7 RBX, RBP, R12-R15 是 callee-saved；其余是 caller-saved 调用者清理栈
Microsoft x64 x86-64 (Windows) 前 4 个参数通过 RCX, RDX, R8, R9 传递（无论整数还是浮点） RBX, RBP, RDI, RSI, R12-R15 是 callee-saved 调用者清理栈

System V AMD64 ABI 示例

下面我们用汇编展示 System V AMD64 调用约定下，函数调用的实际传参过程：

; C 代码: int sum(int a, int b, int c, int d, int e, int f, int g)
; System V AMD64 传参:
;   %rdi = a, %rsi = b, %rdx = c, %rcx = d, %r8 = e, %r9 = f
;   第 7 个参数 g 通过栈传递

; 调用者代码:
sum_function_caller:
    mov     rdi, 1        ; 参数1: a = 1 (放入 RDI)
    mov     rsi, 2        ; 参数2: b = 2 (放入 RSI)
    mov     rdx, 3        ; 参数3: c = 3 (放入 RDX)
    mov     rcx, 4        ; 参数4: d = 4 (放入 RCX)
    mov     r8, 5         ; 参数5: e = 5 (放入 R8)
    mov     r9, 6         ; 参数6: f = 6 (放入 R9)
    push    7             ; 参数7: g = 7 (压栈)
    call    sum_function  ; 调用函数

    add     rsp, 8        ; 调用者清理栈上的参数

; 被调用者代码 (sum 函数内部):
sum_function:
    push    rbp
    mov     rbp, rsp
    ; 参数 a-f 分别在 RDI, RSI, RDX, RCX, R8, R9 中
    ; 参数 g 在 [rbp + 16] 处 (越过返回地址和保存的 rbp)
    mov     eax, edi      ; eax = a
    add     eax, esi      ; eax += b
    add     eax, edx      ; eax += c
    add     eax, ecx      ; eax += d
    add     eax, r8d      ; eax += e
    add     eax, r9d      ; eax += f
    add     eax, [rbp+16] ; eax += g (从栈上取第 7 个参数)
    pop     rbp
    ret
关键理解：调用约定的差异是导致不同语言或不同编译器生成的代码之间无法互相调用的主要原因之一。例如，在 Windows 上用 GCC（遵循 System V ABI）编译的库，不能直接与 MSVC（遵循 Microsoft x64 ABI）编译的程序链接——它们在寄存器使用规则上完全不同。这也是为什么 C 语言中的 extern "C" 声明不仅要处理名字修饰（name mangling），还要确保使用兼容的调用约定。

堆管理与 GC 入门

栈管理是自动的（函数进入时分配，退出时释放），但堆管理则复杂得多。堆是用于存储动态分配的数据的内存区域——它的生命周期不由函数调用范围决定，而是由程序逻辑控制。

malloc/free 实现原理

C 语言的 malloc 和 free 是最基础的内存分配器接口。一个简化版的实现逻辑如下：

// 简化版 malloc/free 实现（仅用于理解原理）
// 实际实现（如 glibc 的 ptmalloc）远比这复杂

typedef struct FreeBlock {
    size_t size;            // 块大小
    struct FreeBlock* next; // 空闲链表指针
} FreeBlock;

static FreeBlock* free_list = NULL;

// 初始化：从操作系统获取一大块内存
void init_heap() {
    free_list = sbrk(HEAP_INIT_SIZE);  // 系统调用
    free_list->size = HEAP_INIT_SIZE - sizeof(FreeBlock);
    free_list->next = NULL;
}

void* malloc(size_t size) {
    // 遍历空闲链表，寻找第一个足够大的块
    FreeBlock* prev = NULL;
    FreeBlock* curr = free_list;

    while (curr != NULL) {
        if (curr->size >= size) {
            // 找到合适块：可能需要分割
            if (curr->size > size + sizeof(FreeBlock) + MIN_BLOCK_SIZE) {
                // 分割：分配前半部分，剩余部分放回空闲链表
                FreeBlock* rest = (FreeBlock*)((char*)curr + sizeof(FreeBlock) + size);
                rest->size = curr->size - size - sizeof(FreeBlock);
                rest->next = curr->next;

                if (prev) prev->next = rest;
                else free_list = rest;

                curr->size = size;
            } else {
                // 不分割：整个块分配出去
                if (prev) prev->next = curr->next;
                else free_list = curr->next;
            }
            return (void*)((char*)curr + sizeof(FreeBlock));
        }
        prev = curr;
        curr = curr->next;
    }
    // 空闲链表不够用：向操作系统申请更多内存
    // ...
}

void free(void* ptr) {
    // 将释放的块重新加入空闲链表
    // （实际实现还需要处理相邻空闲块的合并，以避免内存碎片）
    FreeBlock* block = (FreeBlock*)((char*)ptr - sizeof(FreeBlock));
    block->next = free_list;
    free_list = block;
}

Mark-Sweep GC

与手动内存管理不同，垃圾回收（Garbage Collection, GC）自动识别和回收不再使用的内存。最简单的 GC 算法是Mark-Sweep（标记-清除）：

// Mark-Sweep GC 的简化算法

// 第一阶段：标记 (Mark)
// 从 GC Roots（全局变量、栈上的引用）出发，递归标记所有可达对象
void mark(Object* obj) {
    if (obj == NULL || obj->isMarked) return;
    obj->isMarked = true;  // 标记为存活

    for (Object* child : obj->getReferences()) {
        mark(child);  // 递归标记所有引用对象
    }
}

// 第二阶段：清除 (Sweep)
// 遍历堆，回收所有未被标记的对象
void sweep() {
    for (Object* obj : heap->getAllObjects()) {
        if (!obj->isMarked) {
            free(obj);  // 回收未被标记的对象
        } else {
            obj->isMarked = false;  // 清除标记，为下一次 GC 做准备
        }
    }
}

// 触发 GC：通常当堆内存不足时调用
void garbageCollect() {
    // 从所有根出发标记
    for (Object* root : getGCRoots()) {
        mark(root);
    }
    // 清除未标记的对象
    sweep();
}

Generational GC

Mark-Sweep 有一个严重的问题：每次 GC 都要遍历整个堆，对于长时间运行的程序来说，这会造成明显的"卡顿"。研究表明，大多数对象要么"朝生夕死"（分配后很快变得不可达），要么"长生不死"（存活到程序结束）。基于这个弱代假设（Weak Generational Hypothesis），现代 GC 普遍采用分代回收（Generational GC）策略：

  • 新生代（Young Generation）：新创建的对象放在这里。频繁执行小型 GC（Minor GC），只扫描新生代。大部分对象在第一次 GC 时就被回收了。
  • 老年代（Old Generation）：经过多次 GC 仍然存活的对象被"晋升"到这里。很少执行老年代 GC（Major GC），因为这里面都是"长寿"对象。
  • 永久代/元空间（Metaspace）：存放类的元数据、方法信息等几乎永远不会回收的数据。

分代 GC 的核心优势在于：大多数 GC 只需要扫描堆的一小部分（新生代），大幅减少了 GC 的暂停时间。JVM 的 HotSpot 虚拟机就是分代 GC 的经典实现。

GC 与编译器的关系：虽然 GC 通常被认为是运行时系统的一部分，但编译器在代码生成时也深度参与 GC 的支持工作。编译器需要生成安全点（Safepoint）——在安全点上，GC 可以安全地检查和更新栈上的引用。编译器还需要为每个栈帧生成栈图（Stack Map），告诉 GC 在每一段代码中，栈上的哪些位置存放的是堆对象的引用。这些信息通常由编译器的代码生成阶段嵌入到生成的目标代码中。

异常处理机制

异常处理是现代语言的核心功能，但它的实现机制远比看上去复杂得多。当一个语句抛出异常时，运行时系统必须能够：

  1. 中断当前执行流
  2. 在栈上回溯（unwind），寻找匹配的 catch/异常处理器
  3. 如果找到处理器，展开栈帧（执行 cleanup），跳转到处理器
  4. 如果找不到，调用全局的未处理异常处理器

setjmp/longjmp 方式

这是最原始的异常处理实现方式，C 标准库中就有这两个函数：

#include <setjmp.h>
#include <stdio.h>

jmp_buf env;

void inner() {
    printf("inner: 即将抛出异常\n");
    longjmp(env, 42);  // "抛出异常"，跳回 setjmp 的位置，返回值为 42
    printf("inner: 这行不会执行\n");
}

int main() {
    int result = setjmp(env);  // 记录当前执行位置
    if (result == 0) {
        printf("main: 正常路径，调用 inner\n");
        inner();
    } else {
        printf("main: 捕获异常，代码=%d\n", result);
    }
    return 0;
}
// 输出:
// main: 正常路径，调用 inner
// inner: 即将抛出异常
// main: 捕获异常，代码=42

setjmp/longjmp 的方式简单直接，但存在严重问题：它不处理 C++ 对象的析构、不释放资源、且性能较差（longjmp 需要遍历栈并恢复寄存器）。现代 C++ 和 Java 的异常处理不再使用这种方法。

Table-Driven 异常处理

现代编译器的异常处理采用表驱动（Table-Driven）的方式。编译器在生成代码的同时，生成一系列特殊的表格，描述了：每个程序点对应的异常处理器、try 块的范围、需要执行 cleanup 的局部变量等。

// 编译 C++ 代码生成的异常处理表（概念化）
//
// try { ... throw ... } catch (int e) { ... }
//
// 生成的异常表条目:
//   try_start = 0x1000, try_end = 0x2000
//   catch_type = "int"
//   catch_handler = 0x3000
//   cleanup_actions = [销毁局部对象 A, 销毁局部对象 B]

// 当异常发生时，运行时系统:
// 1. 通过程序计数器 (PC) 查找当前的 try 块
// 2. 检查异常类型是否匹配 catch_type
// 3. 如果匹配：
//    a. 执行从 try_start 到当前 PC 之间所有已构造对象的析构
//    b. 跳转到 catch_handler
// 4. 如果不匹配：继续向上回溯调用者的栈帧

零成本异常（Zero-Cost Exception）

这是 Itanium C++ ABI 定义的异常处理模型，被 GCC 和 Clang 广泛采用。"零成本"的意思是：在没有异常抛出的正常执行路径上，异常处理不产生任何额外开销。不检查异常标志、不更新异常相关状态。所有的异常处理信息存放在单独的表格中（与代码段分离），仅在异常抛出时才被查询。

零成本异常的实现依赖于：

  • LSDA（Language-Specific Data Area）：每个函数在 ELF 文件的 .gcc_except_table 段中有一段异常处理数据，描述了 try 块范围和对应的 handler。
  • 调用栈展开（Unwinding）：异常抛出时，运行时系统使用 .eh_frame 段中的 DWARF 展开信息来逐帧回溯栈。DWARF 展开信息描述了如何恢复每一帧的寄存器（包括栈指针和帧指针），允许运行时"解包"每一层栈帧。
  • 着陆垫（Landing Pad）：每个 try 块的 catch 代码位于一个"着陆垫"中。展开过程中，运行时系统查找当前帧是否在某个 try 块范围内，如果是则跳转到对应的着陆垫。
性能洞察："零成本"指的是正常执行路径的零开销，而不是异常抛出时的零开销。当异常真正被抛出时，表驱动的异常处理需要进行复杂的栈展开操作——查找异常表、解析 DWARF 展开信息、逐帧调用析构函数。这个代价是相当大的（可能耗费数万 CPU 周期）。这就是为什么异常应该仅用于"异常情况"，而不应该用作常规的控制流。在性能关键的代码中，C++ 的 -fno-exceptions 选项可以完全禁用异常支持，消除异常表占用的空间开销。

本章小结

本章我们深入探讨了运行时系统的四个核心方面。栈与栈帧层面，我们学习了函数调用的 prologue/epilogue、栈帧布局（帧指针 vs 栈指针）。调用约定层面，我们了解了 cdecl、stdcall 和 System V AMD64 等不同约定的参数传递和寄存器保存规则。内存管理层面，我们看到了 malloc/free 的简化实现、Mark-Sweep GC 算法、以及分代 GC 的优化原理。最后，异常处理层面，我们学习了从 setjmp/longjmp 到表驱动的零成本异常模型的发展历程。

以上这些知识，连接了编译器后端与操作系统之间的"最后一公里"。理解运行时系统的工作原理，能让你更清楚地知道代码在 CPU 上实际是如何执行的。

从下一章开始，我们将进入编译器的另一个重要话题——错误处理与诊断。用户输入的代码不可能永远正确，一个优秀的编译器不仅要能编译正确的代码，还要能在遇到错误时给出清晰、有用的诊断信息。这是区分"玩具编译器"和"工业级编译器"的关键。敬请期待。
