第5章 语法分析基础

大家好，我是你们的讲师。到目前为止，我们的编译器只能做一件事——把源代码拆成Token。但光有单词是不够的，我们需要知道这些单词之间的结构关系。就像中文句子"我吃饭"——词法分析只是告诉你"我"是代词、"吃"是动词、"饭"是名词，但语法分析会告诉你这是一个"主谓宾"结构，而且语义上是合理的。

语法分析（Syntax Analysis / Parsing）是编译器中最核心、最复杂、也是理论最深厚的一个阶段。可以说，整个编译原理课程中一半的重量都在这里。从这一章开始，我们将深入探讨编译器的心脏。

为什么语法分析如此重要？因为它是编译器中第一个检查"程序是否合法"的阶段。词法分析只关心"字符是否属于语言的字母表"，而语法分析关心的是"这些Token的组合是否遵循语言的文法规则"。一个语法错误（比如少了个括号）会让整个程序变得毫无意义。而且，语法分析的结构化输出——语法树——是编译器后续所有阶段（语义分析、优化、代码生成）的基础。

上下文无关文法定义

我们用什么来精确描述一门编程语言的语法结构？答案就是上下文无关文法（Context-Free Grammar, CFG）——这里"上下文无关"的意思是：一个语法结构的含义不依赖于它出现的上下文环境。

一个CFG由四个部分组成：

  • 终结符（Terminal）：词法分析产出的Token——就是那些不能再被拆分的"单词"。比如 int、+、42、;。
  • 非终结符（Nonterminal）：需要进一步展开的语法成分。比如 expression（表达式）、statement（语句）、declaration（声明）。
  • 产生式（Production）：描述非终结符如何展开为终结符和非终结符的规则。形如 A → α，其中A是非终结符，α是零个或多个终结符/非终结符的序列。
  • 开始符号（Start Symbol）：一个特殊的非终结符，表示整个语言的"根"。所有文法规则都从它开始推导。

让我们用一个非常简单的算术表达式文法来理解这些概念：

// 一个简单的算术表达式文法

// 产生式（Production）：
// 符号说明：→ 读作"定义为"，| 读作"或者"

expr    → expr "+" term
        | expr "-" term
        | term

term    → term "*" factor
        | term "/" factor
        | factor

factor  → "(" expr ")"
        | NUM

// 其中：
//   非终结符: expr, term, factor
//   终结符: "+", "-", "*", "/", "(", ")", NUM
//   开始符号: expr

这个文法描述了带优先级（乘除优先于加减）的算术表达式。注意看，expr 的定义中引用了自身——这就是文法的递归能力，也是CFG比正则表达式更强大的根本原因。

最左推导与最右推导

"推导（Derivation）"这个概念，简单说就是"从开始符号出发，反复使用产生式，直到得到一个完全由终结符组成的序列"的过程。如果推导成功，说明输入的Token序列在语法上是合法的。

考虑表达式 1 + 2 * 3，下面分别用最左推导和最右推导来生成它：

最左推导（Leftmost Derivation）

每一步都替换最左边的非终结符：

expr
→ expr + term           // 替换最左边的 expr
→ term + term           // 替换最左边的 term（expr已被替换）
→ factor + term         // 替换最左边的 factor
→ NUM + term            // 替换最左边的 factor
→ "1" + term            // 拿到具体的数值
→ "1" + term * factor   // 替换最左边的 term（只剩下一个term）
→ "1" + factor * factor
→ "1" + NUM * factor
→ "1" + "2" * factor
→ "1" + "2" * NUM
→ "1" + "2" * "3"

最右推导（Rightmost Derivation）

每一步都替换最右边的非终结符：

expr
→ expr + term               // 替换最右边（但只有一个非终结符）
→ expr + term * factor       // 替换最右边的 term
→ expr + term * NUM          // 替换最右边的 factor
→ expr + term * "3"
→ expr + factor * "3"
→ expr + NUM * "3"
→ expr + "2" * "3"
→ term + "2" * "3"
→ factor + "2" * "3"
→ NUM + "2" * "3"
→ "1" + "2" * "3"
为什么最右推导更重要？因为自底向上的语法分析器（如LR分析器）执行的是最右推导的逆过程——最左归约。所以当你学习第7章的自底向上分析时，你会反复遇到"最右推导"这个概念。相反，自顶向下的分析器（如LL分析器）执行的则是最左推导。这两个"最"字不是形式上的区别——它们决定了分析器的构造方法和能力范围。

规范推导（Canonical Derivation）指的就是最右推导——之所以叫"规范"，是因为在编译器理论和实践中，最右推导被证明具有最好的性质，尤其是在LR分析中。

语法树与AST的区别

许多初学者容易混淆具体语法树（CST, Concrete Syntax Tree，也称Parse Tree）和抽象语法树（AST, Abstract Syntax Tree）。它们的区别非常关键。

具体语法树（CST）

CST是推导过程的"树形记录"——每个终结符和非终结符都是树中的一个节点。它完整保留了文法中的所有信息，包括那些仅用于"语法结构"的辅助节点（比如我们文法中的 term、factor 等中间非终结符）。CST非常"啰嗦"——对于表达式 1 + 2，CST已经包含了相当多的节点。

抽象语法树（AST）

AST只保留程序语义需要的核心信息。它去掉了CST中不需要的中间节点（比如 term、factor），直接表达"操作符-操作数"关系。对于 1 + 2，AST就是一个根节点"+"和两个叶子节点"1"、"2"。

来看一个具体的对比——对于表达式 1 + 2 * 3：

// 具体语法树（CST）——保留了所有文法节点
         expr
        / |  \
     expr +  term
      |      / | \
     term term * factor
      |    |      \
    factor factor  NUM(3)
      |      |
    NUM(1) NUM(2)

// 抽象语法树（AST）——只保留语义核心
       +
      / \
     1   *
        / \
       2   3

CST直接反映了文法结构（term、factor等中间节点都保留），而AST去除了这些"语法糖"，直接表达了运算的优先级和结合关系。在AST中，2 * 3 是 + 的右子节点——这明确表明了乘法先于加法执行。

工程实践：大多数编译器不会显式构建CST。CST太大了——一个100行的C程序，CST可能有上万个节点。相反，语法分析器通常会"边解析边构建AST"：在语法分析的过程中，直接在动作代码中创建AST节点，跳过那些可以省略的中间节点。这就是为什么ANTLR等工具允许你在每条产生式后面附加"动作代码"——你在那里构建AST。如果你不构建AST，语法分析器只是告诉你"合法"或"不合法"，但编译器需要结构化的输出来进行后续阶段。

二义性文法

"二义性（Ambiguity）"是文法设计的一个严重问题。如果一个文法对同一个输入序列可以产生两种或以上不同的语法树，那么这个文法就是二义的（Ambiguous）。

悬空else问题

最经典的二义性例子是"悬空else（Dangling Else）"问题。考虑下面的文法片段：

stmt → if expr then stmt
     | if expr then stmt else stmt
     | other

现在分析输入 if E1 then if E2 then S1 else S2：

它有两种可能的解析方式：

// 解析方式1：else匹配最近的if
if E1 then (if E2 then S1 else S2)

// 解析方式2：else匹配最远的if
if E1 then (if E2 then S1) else S2

这两种解析方式产生的语法树完全不同，程序的行为也因此不同。几乎所有的主流语言（C、C++、Java、JavaScript）都采用了"最近匹配"规则（else匹配离它最近的if），但语言的文法本身如果不加处理，是无法消除这种歧义的。

消除二义性的方法

有三种主流策略：

  1. 改写文法：将文法改写为无二义的形式。比如引入matched_stmt（有else的语句）和unmatched_stmt（没有else的语句）两种非终结符。这会在文法层面彻底消除歧义，但会使文法变得更加复杂。
  2. 优先级和结合性声明：在Yacc/Bison等工具中，使用 %left、%right、%nonassoc 等声明来告诉分析器如何处理有歧义的情况。这种做法不需要改文法，是工程中最常用的方法。
  3. 分析器策略：某些分析器（如LL分析器）默认采用贪心匹配——如果可以匹配更长的产生式，就优先匹配。这个方法简单但不够通用。
方法 优点 缺点 适用场景
改写文法 理论上无懈可击 文法变得庞大且难以维护 学术研究、小语言
优先级声明 简洁、易于理解 依赖特定工具的特性 Yacc/Bison/ANTLR工程实践
分析器策略 无需修改文法 可能导致意外的行为 手写递归下降解析器

一段真实的"踩坑"经历

说到二义性，我有个印象特别深刻的教训。很多年前，我在为一个团队开发的DSL设计语法时，写了一段这样的规则：

// 错误的文法设计！
expr → expr "-" expr     // 减法
     | expr ">" expr     // 大于比较
     | NUM

当时我天真地以为"语法分析器会正确处理所有情况"，结果测试 5 - 3 > 1 时，分析器给出了令人困惑的结果。有的输入按 (5 - 3) > 1 解析（结果是true），有的按 5 - (3 > 1) 解析（结果是4）。

为什么？因为这个文法是二义的！减法 - 和比较 > 之间的优先级没有被文法的层级结构表达出来。在正确的文法中，算术表达式和比较表达式应该在不同的优先级层级上：

// 正确的文法设计——用层级表达优先级
expr     → comparison
comparison → comparison ">" arith_expr
          | arith_expr
arith_expr → arith_expr "-" term
          | term
term     → factor
factor   → NUM | "(" expr ")"

这个层级表达的意思很明确：减法比比较的优先级高。而且这个文法是无二义的——对于任何输入，只有一棵合法的语法树。

关键教训：文法中"优先级"不是一个开关，而是通过层级（Level）来编码的。每一层对应一个优先级层级，高一层的非终结符产生式可以嵌套低一层的非终结符，反之不行。这种层级结构是消除算术和比较表达式二义性的标准方式。我在那之后养成了一个习惯：写文法时先用纸画出优先级层级图，再写产生式。

本章小结

本章我们全面学习了语法分析的理论基础。我们从上下文无关文法（CFG）的定义出发，掌握了终结符、非终结符、产生式、开始符号这四个核心概念。接着讨论了最左推导与最右推导的区别——前者对应自顶向下分析，后者对应自底向上分析。然后我们区分了CST（具体语法树）和AST（抽象语法树）——编译器构建的是AST而不是CST，因为AST更简洁、更接近语义。最后我们分析了文法的二义性问题，特别是著名的"悬空else"问题，以及通过改写文法、优先级声明、分析器策略三种消除方法。

下一章，我们将正式进入自顶向下语法分析的实际构造方法。我们会学习递归下降解析器——这是最直观、最容易手写的解析方法。我们还会讨论FIRST集、FOLLOW集、LL(1)预测分析表以及左递归消除等关键技术。你将体会到"给每个非终结符写一个函数"这种优雅的设计思想。
