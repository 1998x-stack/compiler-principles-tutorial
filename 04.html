第4章 词法分析器实现

大家好，我是你们的讲师。上一章我们学习了词法分析的理论基础——正则表达式和有限自动机。但理论终归要落地。今天，我们就来亲手实现一个词法分析器。

我们会从两个方向入手：第一，用Flex这个现成的词法分析器生成器，快速构建一个功能完整的词法分析器；第二，手写一个简单的词法分析器，理解它的底层工作机制。这种"两条腿走路"的方式会让你既具备工程效率，又掌握底层原理——在实际工作中，你可能大部分时间用Flex/ANTLR，但遇到诡异的Bug时，手写词法分析器的经验会让你知道问题出在哪里。

本章目标：完成一个支持C语言子集的词法分析器，包括关键字、标识符、数字字面量、字符串字面量、运算符和分隔符。同时学会设计Token数据结构、处理常见的词法错误。

Flex语法详解

让我们深入Flex的语法。一个完整的Flex文件包含三个部分：

%{
/* ======= 第一部分：定义段 ======= */
/* 这里的C代码会被直接复制到生成的 lex.yy.c 的开头 */
#include "tokens.h"
#include <stdio.h>

/* 可以定义全局变量和辅助函数 */
int line_num = 1;
%}

/* 正则表达式的别名定义（缩写） */
DIGIT    [0-9]
LETTER   [a-zA-Z_]
IDENT    {LETTER}({LETTER}|{DIGIT})*

/* 启动条件（Start Conditions）：用于处理上下文相关的词法规则 */
%x STRING

%%
/* ======= 第二部分：规则段 ======= */
/* 格式：模式    { 动作 } */

/* 关键字（优先匹配） */
"int"       { return TOKEN_INT; }
"float"     { return TOKEN_FLOAT; }
"if"        { return TOKEN_IF; }
"else"      { return TOKEN_ELSE; }
"while"     { return TOKEN_WHILE; }
"return"    { return TOKEN_RETURN; }

/* 标识符 */
{IDENT}     { yylval.str = strdup(yytext); return TOKEN_IDENT; }

/* 数字字面量 */
{DIGIT}+                { yylval.ival = atoi(yytext); return TOKEN_INT_LIT; }
{DIGIT}+"."{DIGIT}*     { yylval.fval = atof(yytext); return TOKEN_FLOAT_LIT; }

/* 字符串字面量（使用启动条件处理） */
"\""        { BEGIN(STRING); string_buf[0] = '\0'; }
<STRING>"\""        { BEGIN(INITIAL); yylval.str = strdup(string_buf); return TOKEN_STRING; }
<STRING>.           { /* 追加字符到字符串缓冲区 */ }
<STRING>\n          { fprintf(stderr, "第%d行: 未闭合的字符串\n", line_num); }

/* 运算符和分隔符 */
"+"         { return TOKEN_PLUS; }
"-"         { return TOKEN_MINUS; }
"*"         { return TOKEN_MUL; }
"/"         { return TOKEN_DIV; }
"=="        { return TOKEN_EQ; }
"!="        { return TOKEN_NE; }
"<"         { return TOKEN_LT; }
"<="        { return TOKEN_LE; }
";"         { return TOKEN_SEMI; }
"("         { return TOKEN_LPAREN; }
")"         { return TOKEN_RPAREN; }
"{"         { return TOKEN_LBRACE; }
"}"         { return TOKEN_RBRACE; }

/* 跳过空白和注释 */
[ \t\r]+    { /* 忽略空白 */ }
\n          { line_num++; }
"//"[^\n]*  { /* 忽略单行注释 */ }
"/*"        { /* 多行注释开始，需要使用启动条件 */ }

/* 非法字符 */
.           { fprintf(stderr, "第%d行: 非法字符 '%s'\n", line_num, yytext); }

%%
/* ======= 第三部分：辅助函数段 ======= */

int main(int argc, char **argv) {
    if (argc > 1) {
        yyin = fopen(argv[1], "r");
        if (!yyin) {
            perror("无法打开文件");
            return 1;
        }
    }

    int token;
    while ((token = yylex()) != 0) {
        printf("Token: %d, 文本: %s, 行号: %d\n", token, yytext, line_num);
    }
    return 0;
}

int yywrap() {
    return 1;  /* 通知Flex文件结束 */
}

yylex() 的工作方式

yylex() 是Flex生成的词法分析器的核心函数。每次调用它，它都会从输入中读取字符，找到匹配最长的规则，执行对应的动作，然后返回一个整数（Token类型）。如果返回0，表示输入结束。

Flex内部使用了一个重要的变量yytext——它指向当前匹配到的文本内容。还有一个全局变量yylval——通常用来传递Token的附加信息（比如标识符的字符串、数字的值）。yylval的类型默认是int，但你可以通过定义YYSTYPE宏来改变它。

启动条件的妙用：字符串字面量的处理是启动条件（Start Condition）的一个经典应用。当遇到第一个双引号时，用 BEGIN(STRING) 切换到字符串模式，在这个模式下，除了双引号之外的所有字符都被当作字符串内容处理。直到遇到结束的双引号，用 BEGIN(INITIAL) 回到初始模式。这样，同一个词法分析器在不同上下文中可以做不同的事情——这是Flex最强大的特性之一。

手写递归下降词法分析器

虽然Flex已经非常好用，但理解手写词法分析器的原理同样重要。有时候你需要在资源受限的环境（比如嵌入式系统）中编写编译器，或者你的语言有非常特殊的词法规则不适合Flex的模式。在这些情况下，手写词法分析器是唯一的选择。

手写词法分析器实际上就是一个状态机——用一个变量记录当前状态，根据读入的字符决定如何转移到下一个状态。

一个简单的状态机实现

#include <stdio.h>
#include <ctype.h>
#include <string.h>

/* Token类型枚举 */
typedef enum {
    TOKEN_EOF = 0,
    TOKEN_IDENT,
    TOKEN_NUMBER,
    TOKEN_PLUS, TOKEN_MINUS, TOKEN_MUL, TOKEN_DIV,
    TOKEN_LPAREN, TOKEN_RPAREN,
    TOKEN_SEMI,
    TOKEN_ERROR
} TokenType;

/* Token结构 */
typedef struct {
    TokenType type;
    char lexeme[256];
    int line;
    int column;
    int int_value;  /* 如果是数字Token */
} Token;

/* 词法分析器状态 */
typedef struct {
    const char *input;
    int pos;
    int line;
    int column;
} Lexer;

/* 初始化词法分析器 */
void lexer_init(Lexer *lexer, const char *input) {
    lexer->input = input;
    lexer->pos = 0;
    lexer->line = 1;
    lexer->column = 1;
}

/* 跳过空白 */
void lexer_skip_whitespace(Lexer *lexer) {
    while (lexer->input[lexer->pos] != '\0') {
        char c = lexer->input[lexer->pos];
        if (c == ' ' || c == '\t' || c == '\r') {
            lexer->pos++;
            lexer->column++;
        } else if (c == '\n') {
            lexer->pos++;
            lexer->line++;
            lexer->column = 1;
        } else {
            break;
        }
    }
}

/* 获取下一个Token */
Token lexer_next(Lexer *lexer) {
    Token token = {0};
    lexer_skip_whitespace(lexer);

    token.line = lexer->line;
    token.column = lexer->column;

    char c = lexer->input[lexer->pos];

    if (c == '\0') {
        token.type = TOKEN_EOF;
        strcpy(token.lexeme, "EOF");
        return token;
    }

    /* 标识符 or 关键字 */
    if (isalpha(c) || c == '_') {
        int i = 0;
        while (isalnum(lexer->input[lexer->pos]) || lexer->input[lexer->pos] == '_') {
            token.lexeme[i++] = lexer->input[lexer->pos++];
            lexer->column++;
        }
        token.lexeme[i] = '\0';
        token.type = TOKEN_IDENT;
        return token;
    }

    /* 数字字面量 */
    if (isdigit(c)) {
        int i = 0;
        token.int_value = 0;
        while (isdigit(lexer->input[lexer->pos])) {
            token.int_value = token.int_value * 10 + (lexer->input[lexer->pos] - '0');
            token.lexeme[i++] = lexer->input[lexer->pos++];
            lexer->column++;
        }
        token.lexeme[i] = '\0';
        token.type = TOKEN_NUMBER;
        return token;
    }

    /* 运算符和分隔符 */
    token.lexeme[0] = c;
    token.lexeme[1] = '\0';
    lexer->pos++;
    lexer->column++;

    switch (c) {
        case '+': token.type = TOKEN_PLUS; break;
        case '-': token.type = TOKEN_MINUS; break;
        case '*': token.type = TOKEN_MUL; break;
        case '/': token.type = TOKEN_DIV; break;
        case '(': token.type = TOKEN_LPAREN; break;
        case ')': token.type = TOKEN_RPAREN; break;
        case ';': token.type = TOKEN_SEMI; break;
        default:
            token.type = TOKEN_ERROR;
            snprintf(token.lexeme, sizeof(token.lexeme),
                     "非法字符: '%c' (0x%02x)", c, c);
            break;
    }
    return token;
}

/* 演示使用 */
int main() {
    const char *code = "sum = 42 + 18;";
    Lexer lexer;
    lexer_init(&lexer, code);

    Token token;
    while ((token = lexer_next(&lexer)).type != TOKEN_EOF) {
        if (token.type == TOKEN_ERROR) {
            printf("第%d行: 错误 - %s\n", token.line, token.lexeme);
        } else {
            printf("第%d行第%d列: Token=%d, 词素=%s",
                   token.line, token.column, token.type, token.lexeme);
            if (token.type == TOKEN_NUMBER) {
                printf(", 值=%d", token.int_value);
            }
            printf("\n");
        }
    }
    return 0;
}

缓冲区管理

在真实编译器中，词法分析器不能简单地把整个源代码一次性加载到内存——源代码文件可能非常大（几百MB的C++文件并不罕见）。因此，Flex和手写词法分析器都会使用缓冲区管理技术：

  • 输入缓冲区：按块读取源代码（通常4KB到8KB），维护一个指针指示当前读取位置。
  • 回退缓冲区：词法分析器经常需要"偷看"下一个字符来决定当前Token的边界。如果"偷看"后发现这个字符不属于当前Token，需要能"退回"这个字符。
  • 双缓冲区：Flex使用双缓冲区实现高效的输入处理——当一个缓冲区读完后，自动切换到另一个缓冲区并开始填充新的数据。
缓冲区管理的陷阱：手写词法分析器时，最容易出Bug的地方就是回退（unread）逻辑。比如识别"<="时需要先读取"="，发现不是"="后要把它放回去。如果回退逻辑不严谨，就会导致Token边界错误。这也是为什么很多编译器教科书专门讲解"lookahead"设计模式——它用一个固定的lookahead位置来处理预读，避免对输入流的"反悔"操作。

Token数据结构设计

Token是编译器中最重要的数据结构之一——它是词法分析器和语法分析器之间的桥梁。一个设计良好的Token结构可以大大简化后续阶段的工作。

Token类型枚举

Token类型通常用一个枚举来定义，涵盖所有可能的词法元素：

// tokens.h — Token类型定义

typedef enum {
    // 关键字 (100-199)
    TOKEN_INT = 100,
    TOKEN_FLOAT = 101,
    TOKEN_IF = 102,
    TOKEN_ELSE = 103,
    TOKEN_WHILE = 104,
    TOKEN_RETURN = 105,
    TOKEN_VOID = 106,

    // 标识符和字面量 (200-299)
    TOKEN_IDENT = 200,
    TOKEN_INT_LIT = 201,
    TOKEN_FLOAT_LIT = 202,
    TOKEN_STRING_LIT = 203,

    // 运算符 (300-399)
    TOKEN_PLUS = 300,
    TOKEN_MINUS = 301,
    TOKEN_MUL = 302,
    TOKEN_DIV = 303,
    TOKEN_ASSIGN = 304,
    TOKEN_EQ = 305,      // ==
    TOKEN_NE = 306,      // !=
    TOKEN_LT = 307,      // <
    TOKEN_LE = 308,      // <=
    TOKEN_GT = 309,      // >
    TOKEN_GE = 310,      // >=

    // 分隔符 (400-499)
    TOKEN_SEMI = 400,    // ;
    TOKEN_LPAREN = 401,  // (
    TOKEN_RPAREN = 402,  // )
    TOKEN_LBRACE = 403,  // {
    TOKEN_RBRACE = 404,  // }
    TOKEN_COMMA = 405,   // ,

    // 特殊Token
    TOKEN_EOF = 0,
    TOKEN_ERROR = -1
} TokenType;

位置信息

每个Token都应该记录它在源代码中的位置，以便在编译错误时给出精确的提示：

typedef struct {
    int line;     /* 行号（从1开始） */
    int column;   /* 列号（从1开始） */
    int offset;   /* 在源文件中的字节偏移 */
} SourceLocation;

typedef struct {
    TokenType type;
    SourceLocation loc;
    union {
        char *str_value;      /* 标识符/字符串的值 */
        int int_value;        /* 整数字面量的值 */
        double float_value;   /* 浮点字面量的值 */
    } value;
} Token;

这样设计的好处是：语法分析器在报告错误时，可以直接输出"第5行第12列: 期望 ';' 但得到 '}' "，让程序员一眼就能定位问题。Clang之所以以友好的错误信息著称，很大程度上就是因为它在每一个Token的位置信息上做得非常精细。

常见词法错误处理

词法分析器的错误处理原则是：尽量恢复，不要终止。也就是说，当遇到一个词法错误时，应该能报告错误并继续扫描，这样编译一次就能发现所有词法错误，而不是"发现一个就停"。

以下是几种常见的词法错误及处理策略：

错误类型 例子 处理策略
非法字符 @、` 跳过该字符，报告"非法字符"，继续扫描
未闭合字符串 "hello world 报告"未闭合的字符串"，假设字符串在行尾结束
数字溢出 99999999999999999999 报告"整数溢出"，截断到最大值
浮点格式错误 1.2.3 识别"1.2"，报告后续字符的格式错误
不完整的多行注释 /* 没有结束 报告"未闭合的注释"，在文件末尾报错
一个实用的技巧：在开发词法分析器时，创建一个"Token转字符串"的调试函数非常有用。像 const char *token_name(TokenType t) 这样的函数，可以将Token类型转换为可读的字符串。当你调试语法分析器时，可以用它来打印Token序列，快速验证词法分析的结果是否正确。这个简单的工具可以节省你大量的调试时间。

一段真实的"踩坑"经历

在我第一次亲手从头实现词法分析器时，遇到了一个让人抓狂的Bug。我们的语言中有一个 .. 运算符（用于范围表达式，类似Rust的 1..5），还有一个 . 运算符（用于访问成员）。但问题来了——输入 1..5 时，词法分析器会把它识别为：数字 1、点 .、点 .、数字 5，而不是我们期望的数字 1、范围运算符 ..、数字 5。

为什么？因为我设计的词法分析器在识别出数字 1 后，下一个字符是 .，它直接匹配了单点规则并返回，根本没给"两点"模式一个机会。

解决方案很简单——最长匹配原则的应用：在匹配运算符时，总是先尝试匹配更长的模式。在Flex中就是先写 .. 规则再写 . 规则。在手写词法分析器中，就是在处理小数点时先"预读"下一个字符，看看是不是也是点。

/* 手写词法分析器中的最长匹配处理 */
if (c == '.') {
    if (peek() == '.') {
        advance();  /* 消费第二个点 */
        return TOKEN_DOTDOT;  /* 返回".." */
    }
    return TOKEN_DOT;  /* 返回单个"." */
}

这个经历让我深刻理解了为什么Flex默认采用最长匹配策略——这不是一个随意的设计决定，而是解决实际词法歧义的必然选择。

教训：手写词法分析器时，"预读"是最容易出错的操作。推荐的模式是：把"预读"封装成一个明确的函数（如 peek()），把"消费字符"也封装成一个函数（如 advance()）。永远不要让预读和消费的逻辑散落在代码各处——这是Bug的温床。一个经过良好设计的词法分析器，其核心循环应该清晰到看一眼就能理解。

本章小结

这一章我们把词法分析的理论付诸实践。我们从Flex的完整语法入手，学习了定义段、规则段、辅助函数段三部分各自的职责，以及启动条件、yylex()工作机制等核心概念。然后我们手写了一个完整的词法分析器，理解了状态机的本质、缓冲区管理的重要性和"预读"的处理技巧。接着讨论了Token数据结构设计的工程决策——类型枚举、位置信息、值联合体。最后，我们整理了常见词法错误的处理策略。

词法分析器是编译器的"门面"——它是处理源代码的第一个阶段，它的健壮性直接关系到编译器的整体用户体验。一个能在报错时给出精确位置、能一次性发现所有词法错误的分析器，会为后续阶段的调试节省大量时间。

下一章，我们将进入编译器的核心阶段——语法分析。词法分析给了我们Token序列，但Token之间的结构关系是什么？int a = 1 + 2 * 3 和 int a = 1 + 2 * 3 ; 的Token序列虽然差不多，但后者才是合法的程序——语法分析就是用来判定这个合法性的。
