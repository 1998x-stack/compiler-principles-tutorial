第3章 词法分析基础

大家好，我是你们的讲师。从这一章开始，我们将正式踏入编译器的内部世界。编译器的第一道工序叫做词法分析（Lexical Analysis）——它把源代码（一串字符）拆分为一个个有意义的"单词"，也就是Token。

你可能会觉得这不就是"字符串分割"吗？有什么难的？但真实情况远比你想象的精妙。一个编程语言的关键字有几十个，标识符的命名规则复杂多样，数字字面量有整数、浮点、科学计数法、十六进制，字符串里还有转义序列……要高效且无歧义地处理所有这些情况，需要一套严谨的理论工具。这套工具就是正则表达式和有限自动机。

为什么词法分析值得单独研究？将词法分析与后续的语法分析分离，是编译器设计中最重要的架构决策之一。词法分析器的实现简单、高效（可以用一个有限状态机在O(n)时间内完成），而且它可以大幅简化语法分析器的设计——语法分析器不需要关心空格、注释、标识符的字符级细节。这种"分层"思想贯穿了整个编译器设计。

词法分析的作用

词法分析器的输入是源代码字符串，输出是Token序列。每个Token包含类型和值两个基本信息。比如对于下面这段简单的代码：

int main() {
    return 42;
}

词法分析器会生成这样的Token序列：

<KEYWORD: "int">
<IDENTIFIER: "main">
<LPAREN: "(">
<RPAREN: ")">
<LBRACE: "{">
<KEYWORD: "return">
<INT_LITERAL: 42>
<SEMICOLON: ";">
<RBRACE: "}">
<EOF>

词法分析阶段做了以下几件重要的事情：

  • 去噪音：过滤掉空格、换行、注释等不影响程序语义的字符。
  • 归类：将字符序列归类为关键字、标识符、字面量、运算符、分隔符等类型。
  • 预处理：对于数字字面量，从字符串格式转换为数值（比如"0xFF"转换为255）。
  • 标记位置：记录每个Token在源代码中的行列号，方便后续的错误报告。

一个高效的词法分析器可以轻松达到每秒处理数百万行代码的速度。事实上，词法分析是整个编译流水线中最快的阶段——它通常只占用总编译时间的5%左右。

正则表达式入门

词法分析的核心工具是正则表达式（Regular Expression）。正则表达式是一种描述字符串模式（Pattern）的形式化语言。它的表达能力刚好足够描述编程语言的词法结构——既不会太弱（无法描述数字、标识符等结构），也不会太强（不会像上下文无关文法那样需要递归能力）。

基本构造

语法 含义 示例 匹配
a 字符a自身 cat "cat"
. 任意单个字符（除换行） c.t "cat", "cot", "c.t"
[abc] 字符类：a、b或c中任一 [0-9] "0"到"9"的任何数字
ab* a后跟零个或多个b 10* "1", "10", "100", "1000"
ab+ a后跟一个或多个b 10+ "10", "100", "1000"（不含"1"）
ab? a后跟零个或一个b 10? "1", "10"
a|b a或b（选择） int|float "int"或"float"
(...) 分组 (ab)+ "ab", "abab", "ababab"

词法规则中的正则表达式

实际编译器开发中，我们常用正则表达式来描述各种Token的模式。下面是一些典型例子：

# C语言中常见Token的正则表达式模式

# 标识符（Identifier）：字母或下划线开头，后跟零个或多个字母/数字/下划线
标识符: [a-zA-Z_][a-zA-Z0-9_]*

# 整数（Integer）：十进制、八进制（0开头）、十六进制（0x开头）
十进制: [1-9][0-9]*
八进制: 0[0-7]*
十六进制: 0[xX][0-9a-fA-F]+
整数: (十进制)|(八进制)|(十六进制)

# 浮点数（Float）：带小数点的数字
浮点数: [0-9]+"."[0-9]*

# 字符串字面量：双引号包裹，支持转义
字符串: "\"" ("\\" . | [^"\\])* "\""

# 注释：// 到行尾
单行注释: "//" [^\n]*

# 空白字符（跳过）
空白: [ \t\n\r]+
注意：正则表达式虽然强大，但有一个重要的局限性——它无法处理嵌套结构。比如你不能用一个正则表达式来匹配"括号嵌套"的结构（如 ( ( ) )）。这正是为什么词法分析之后还需要语法分析——语法分析使用上下文无关文法，它具备递归能力，可以处理嵌套结构。词法分析和语法分析的"分工边界"就在于——有递归结构的地方属于语法分析，没有递归结构的地方属于词法分析。

有限自动机

正则表达式是一种描述性的工具——它告诉我们"什么样的字符串是合法的Token"。但编译器是一个程序，它需要一种算法来高效地识别这些Token。这种算法就是有限自动机（Finite Automaton）。

有限自动机是一个抽象的计算模型，它有一个有限的状态集合，根据输入的字符从一个状态转移到另一个状态。一个Token被识别出来，当且仅当自动机在处理完该Token的所有字符后到达一个接受状态。

NFA vs DFA

有限自动机有两种形式：

  • NFA（非确定性有限自动机）：在同一个状态下，对于同一个输入字符，可能有多个下一个状态可以选择。而且NFA允许"空转移"（不需要输入字符就可以跳转）。NFA的优点是"直观"——从正则表达式直接转换过来很容易。缺点是模拟NFA需要回溯，最坏情况下时间复杂度是指数级的。
  • DFA（确定性有限自动机）：在同一个状态下，对于同一个输入字符，最多只有一个下一个状态。DFA没有空转移。DFA的优点是"高效"——模拟DFA只需要O(n)时间（n是输入长度）。缺点是从正则表达式构造DFA比较麻烦。

实际编译器中的词法分析器几乎毫无例外地使用DFA——因为效率是关键。但编译器开发者不需要手动设计DFA；他们只需提供正则表达式，然后使用子集构造法（Subset Construction）自动将NFA转换为等价的DFA。

子集构造法

子集构造法（也称为"powerset construction"）的核心思想是：NFA的"状态"是单个状态，但DFA的"状态"是NFA状态的集合。NFA在某个时刻"可能处于"哪些状态？这个状态集合就是DFA的一个状态。

算法的基本步骤：

  1. DFA的初始状态 = NFA初始状态的ε-闭包（从初始状态出发，经过零次或多次空转移能到达的所有状态）。
  2. 对于DFA中每个未处理的状态（它是一个NFA状态集合），对于每个输入字符，计算从这个状态集合出发经过该字符能到达的所有NFA状态的ε-闭包。
  3. 如果这个新的状态集合还没有被加入DFA，则加入它。
  4. 重复步骤2-3直到没有新的状态产生。

这个过程很抽象，但别担心——你基本不需要手动实现它。工具如Lex和Flex已经帮你做好了。

直观理解：你可以把NFA想象成一个"有很多备选方案"的猜谜游戏——你同时尝试所有可能的路径，但你需要记录所有可能的位置。而DFA则是一个"确定路线"的导航——每一步你都知道自己在哪里，不需要猜测。词法分析器使用DFA，因为编译器不需要猜测——它需要的是确定性、线性的性能。

Lex/Flex简介

手工编写词法分析器虽然可行（我们会在下一章实现一个），但在工程实践中，99%的情况下你会使用词法分析器生成器。你只需要提供词法规则（正则表达式 + 对应的动作），工具会自动生成一个高效的词法分析器C代码。

其中最著名的工具是Lex（由Mike Lesk和Eric Schmidt在1975年为Unix开发）和它的开源版本Flex（Fast Lexical Analyzer，由Vern Paxson在1987年开发）。

.l文件格式

Flex的输入文件（通常扩展名为.l）分为三个部分，用%%分隔：

/* 定义段：包含C代码的包含语句、宏定义等 */
%{
#include <stdio.h>
%}

/* 这里可以定义正则表达式的缩写 */
DIGIT    [0-9]
LETTER   [a-zA-Z]
IDENT    {LETTER}({LETTER}|{DIGIT})*

%%
/* 规则段：模式 + 动作 */
{IDENT}     { printf("标识符: %s\n", yytext); }
{DIGIT}+    { printf("整数: %s\n", yytext); }
"+"         { printf("加号\n"); }
"-"         { printf("减号\n"); }
"*"         { printf("乘号\n"); }
"/"         { printf("除号\n"); }
"("         { printf("左括号\n"); }
")"         { printf("右括号\n"); }
[ \t\n]     { /* 跳过空白 */ }
.           { printf("未知字符: %s\n", yytext); }

%%
/* 辅助函数段：C的辅助函数 */
int main() {
    yylex();    /* 启动词法分析 */
    return 0;
}

使用Flex处理这个文件很简单：

flex 词法规则.l    # 生成 lex.yy.c
gcc lex.yy.c -lfl  # 编译
./a.out            # 运行

Flex生成的词法分析器非常高效——它生成的是一个表格驱动的DFA，识别速度与输入长度呈线性关系。而且它内置支持"最长匹配"原则——如果有多个模式都可以匹配当前的输入流，Flex会选择匹配最长的那个。如果长度相同，则选择在.l文件中出现更早的那个规则。

工程师的智慧：最长匹配原则非常重要。考虑一个场景——标识符规则 [a-zA-Z_][a-zA-Z0-9_]* 和关键字规则 if 同时匹配输入"if"。如果没有最长匹配，"if"作为关键字可以匹配3个字符，但作为标识符其实可以匹配更长的"ifx"。最长匹配保证了标识符不会被错误地截断。而关键字之所以能被正确识别，是因为词法分析器在处理时通常将关键字规则放在标识符规则之前，先尝试关键字匹配——这也是Flex"优先使用更早出现的规则"的设计意图。

一段真实的"踩坑"经历

几年前，我在一个团队中负责为某公司的内部DSL开发编译器。词法分析部分用了Flex。有一天，测试人员报告了一个诡异的Bug：在某些情况下，带有下划线的变量名（比如 my_var）会在编译时被错误地识别为两个Token——my 和 var。

我检查了词法规则文件，发现标识符的正则表达式是这样写的：

[a-zA-Z]+    { /* 作为标识符处理 */ }
"_"          { /* 作为下划线处理 */ }

看到问题了吗？标识符规则 [a-zA-Z]+ 不包含下划线！所以 my_var 被拆成了 my（匹配标识符）、_（匹配下划线）、var（匹配标识符）。修复很简单：

[a-zA-Z_][a-zA-Z0-9_]*    { /* 作为标识符处理 */ }

这个Bug的教训是：词法规则的边界定义要精确。很多编程语言允许标识符中包含下划线，但你和一个C语言的关键字不同——标识符的规则必须完整涵盖所有合法字符。看似微小的遗漏，就会导致编译器把合法的程序当作错误的语法来解析。

值得警惕的是：这个Bug之所以"诡异"，是因为它只在特定的变量名上出现，且错误信息让人摸不着头脑——后面的语法分析器报告"语法错误"，而不是词法分析器报错。Bug的"表现地点"往往不是"根源地点"，这是编译器调试最困扰人的特点之一。理解每个阶段做了什么、没做什么，是有效调试编译器的前提。
