第11章 中间表示(IR)

大家好，我是你们的讲师。在前面的章节中，我们走完了编译器"前端"的全部旅程：源代码经过词法分析、语法分析、语义分析，变成了一个带类型标注且通过语义验证的 AST。现在的问题是：接下来怎么才能把这个 AST"翻译"成机器能运行的代码？

如果我们直接针对 x86-64 架构生成代码，那么当我们需要支持 ARM 架构时，就要重新写整个代码生成器。如果我们直接生成优化过的代码，那么每种优化都要跟目标架构绑死。历史告诉我们："一次编写，到处重写"是极其糟糕的工程实践。编译器的设计师们很早就意识到，需要在前端和后端之间插入一个中间表示（Intermediate Representation, IR）——一个独立于源语言和目标机器的程序表示形式。

IR 的价值：IR 将编译器解耦为三个独立的模块：前端（源语言 → IR）、优化器（IR → 优化后的 IR）、后端（IR → 目标机器码）。这意味着支持一门新语言只需要写一个前端，支持一个新架构只需要写一个后端，而优化器可以被所有前端和后端共享。这就是 GCC 支持 7+ 种前端语言和 50+ 种目标架构的秘密，也是 LLVM 生态成功的核心设计理念。

中间表示的作用

IR 的设计目标是"站在前端和后端之间"，具体来说它需要满足以下几个需求：

  • 与源语言无关：无论是 C、Rust 还是 Kotlin，编译到同一个 IR 后都可以使用同一套优化器和后端。这意味着 IR 不能保留源语言的特定语义特征（如 C 的指针算术、Java 的异常处理）。
  • 与目标机器无关：IR 不应该暴露特定架构的寄存器数量、指令集特性或调用约定。这样同一个 IR 可以被编译到 x86、ARM、RISC-V 等不同平台。
  • 易于优化：IR 应该使常见的优化（常量折叠、死代码消除、循环优化）易于实现。如果 IR 太"高级"，优化器需要做很多解构工作；如果 IR 太"低级"，优化器又丢失了高层语义信息。
  • 易于生成代码：后端应该能从 IR 相对直接地映射到目标指令。如果 IR 过于抽象，指令选择会变得非常复杂。

历史上出现过许多种 IR 设计，从高级的 AST 本身（有些编译器直接在 AST 上做优化），到各种图形化 IR（如程序依赖图 PDG），再到今天最主流的两类：三地址码和静态单赋值形式（SSA）。

三地址码（TAC）

三地址码（Three-Address Code, TAC）是最经典的 IR 形式之一。顾名思义，每条指令最多涉及三个地址（两个操作数和一个结果）：

result = operand1 operator operand2

这里的"地址"可以是变量名、常量、编译器生成的临时变量。三地址码之所以经典，是因为它将复杂的表达式拆解为一系列简单的原子操作，每个操作只做一件简单的事——这极大地方便了后续的优化和代码生成。

从 AST 到三地址码

让我们看一个例子。下面这段源代码：

int a = 5;
int b = 10;
int c = (a + b) * 2 - a;

会被编译成以下三地址码序列：

t1 = 5           // 常量 5 赋给临时变量 t1
a = t1           // a = 5
t2 = 10          // 常量 10 赋给临时变量 t2
b = t2           // b = 10
t3 = a + b       // 计算 a + b，结果存入 t3
t4 = t3 * 2      // 计算 t3 * 2，结果存入 t4
t5 = t4 - a      // 计算 t4 - a，结果存入 t5
c = t5           // c = 最终结果

注意我们引入了临时变量 t1, t2, t3, t4, t5。这些变量由编译器自动生成，用于保存中间计算结果。源语言中的复杂表达式 (a + b) * 2 - a 被分解为 3 条简单的三地址指令，每条指令只包含一个运算。这种形式不仅便于优化（可以独立分析每条指令），也便于生成汇编代码（每条三地址指令大致对应 1-2 条汇编指令）。

常见指令类型

指令类型 格式 示例
赋值 x = y a = b
二元运算 x = y op z t1 = a + b
一元运算 x = op y t2 = -t1
拷贝赋值 x = y c = t5
无条件跳转 goto L goto L1
条件跳转 if x relop y goto L if a < b goto L2
函数调用 call f, args t3 = call foo(a, b)
函数返回 return x return t3
数组访问 x = y[i] t4 = arr[t5]
指针操作 x = *y, *x = y t6 = *ptr

静态单赋值形式（SSA）

三地址码虽然好用，但有一个根本性的缺陷：它不便于数据流分析。考虑以下代码：

x = 1
x = x + 1
y = x * 2

问题来了：y = x * 2 中的 x 引用的是哪个 x？是初始值 1，还是加 1 后的 2？人眼能看出来是第二个，但从编译器分析的角度，我们需要做到达定值（reaching definition）分析才能确定。而如果变量可以被多次赋值，这种分析会变得相当复杂。

静态单赋值形式（Static Single Assignment, SSA）正是为了解决这个问题而设计的。SSA 的核心规则简单而优雅：每个变量只被赋值一次，并且每个变量在被赋值之前必须唯一定义。

Phi 函数

如果每个变量只能赋值一次，那如何处理程序中的分支呢？比如：

if (condition)
    x = 1
else
    x = 2
y = x

在 if-else 分支中，x 在两个不同的地方被赋值。合并之后，y 的取值取决于走的是哪个分支。SSA 用 phi（φ）函数 来解决这个难题：

// 转换为 SSA 形式后的代码
if (condition)
    x1 = 1
else
    x2 = 2
x3 = phi(x1, x2)   // x3 的值: 如果从 then 分支来则为 x1，否则为 x2
y1 = x3

phi 函数是一个"虚构"的指令——它不执行任何计算，只是告诉编译器："这个变量的值取决于控制流从哪里来"。如果代码是从 then 分支执行到这个合并点的，x3 就等于 x1；如果是从 else 分支来的，x3 就等于 x2。

理解 phi 函数：很多初学者会觉得 phi 函数很神秘。实际上，你可以把 phi 理解为编译器插入在控制流汇合点的一个"选择器"——它根据前驱基本块的不同，选择不同的值。在最终生成机器码时，phi 函数会被解析为实际的选择逻辑（通常在寄存器分配阶段实现为 move 指令）。phi 函数不是真实 CPU 能执行的指令，它是为了方便编译器的数据流分析而存在的抽象。

支配边界与 Phi 函数插入

SSA 构造中最关键的问题是：在哪些位置需要插入 phi 函数？答案是由支配边界（Dominance Frontier）决定的。不严谨地说，如果一个变量在某个基本块 B 中定义，那么在所有被 B 支配（dominate）的基本块中都不需要 phi 函数——因为只要到达这些基本块，必然经过了 B，所以变量的定义是唯一确定的。但在 B 的支配边界（B 支配结束的地方），可能有来自不同路径的代码汇合，此时就需要插入 phi 函数。

SSA 的构造分为两步：

  1. 插入 phi 函数：在需要的地方插入 phi 指令。算法会遍历所有变量的定义点，然后在它们的支配边界处插入 phi 函数。
  2. 变量重命名：为每个变量添加版本号（x1, x2, x3...）。当经过 phi 函数时，使用新的版本号；当引用变量时，使用当前最新的版本号。
理解支配性：基本块 A 支配基本块 B，当且仅当从控制流入口到 B 的所有路径都必须经过 A。如果你把控制流图画成一个有向图，那么支配关系就是"必经之路"的关系。支配边界则是从支配区域"走到"非支配区域的边界点。这个概念的严格定义需要图论知识，但直觉上很简单：一个变量的定义如果只在某个区域内有效，那么在该区域的边界上就需要 phi 函数来"合并"不同的可能值。

基本块与控制流图

无论是三地址码还是 SSA，指令都不是随意排列的——它们被组织在基本块（Basic Block, BB）中，基本块之间通过控制流图（Control Flow Graph, CFG）连接。

基本块的划分

基本块是满足两个条件的最大指令序列：

  • 单一入口：只有第一条指令可能是跳转目标（除非从第一条开始，不可能从中间进入）。
  • 单一出口：只有最后一条指令可能是跳转语句或终止语句（除非执行到最后一条，不可能从中间跳出）。

划分基本块的算法很简单：

1. 确定所有入口指令（leader）：
   - 程序的第一条指令是 leader
   - 任何跳转指令的目标指令是 leader
   - 任何跳转指令的下一条指令是 leader

2. 从每个 leader 开始，直到下一个 leader 之前（或程序结束）
   -> 这个区间就是一个基本块

CFG 的构建

得到基本块列表后，我们通过分析基本块之间的跳转关系来构建 CFG：

// 对于每个基本块 B:
for (每个以 B 结尾的跳转指令) {
    if (条件跳转) {
        addEdge(B, trueTarget);   // 条件成立
        addEdge(B, falseTarget);  // 条件不成立（fall-through）
    } else if (无条件跳转) {
        addEdge(B, target);
    } else {
        // 没有跳转：顺序执行到下一个基本块
        addEdge(B, nextBlock);
    }
}

构建出来的 CFG 是一个有向图，其中：

  • 节点 = 基本块
  • 边 = 控制流转移（跳转或顺序执行）
  • 有一个入口节点和一个或多个出口节点

支配树

在 CFG 之上，我们可以构建支配树（Dominator Tree）：

// 支配关系示例
//
//     CFG:             支配树:
//     entry            entry
//       |                |
//       B1               B1
//      /  \             /  \
//     B2  B3           B2  B3
//      \  /             \  /
//       B4              B4
//       |                |
//      exit             exit
//
// B1 支配所有节点（因为所有路径都必须经过入口）
// B2 只支配 B2 自身
// B3 只支配 B3 自身
// B4 被 B1 支配（所有到 B4 的路径都经过 B1）
// B4 不被 B2 或 B3 支配（有路径可以不经 B2 或 B3 到达 B4）
为什么支配树很重要：支配树是编译器优化的核心工具之一。它用于：SSA 构造中的 phi 函数插入位置计算、循环检测（循环头的特征是"被自身支配"）、代码移动（如循环不变式外提需要确保支配性）、还有各种基于控制流的优化分析。几乎每个重要的优化 pass 都会查询支配关系。理解支配树 = 理解现代编译器优化的基石。

本章小结

本章介绍了编译器架构中承上启下的关键一环——中间表示（IR）。我们了解了 IR 的设计目标（解耦前端与后端、便利优化），学习了经典的线性 IR——三地址码（TAC）的指令格式与生成方法，深入探讨了 SSA 形式的原理（唯一赋值、phi 函数、支配边界），以及基本块划分和 CFG 构建的基础知识。

下一章，我们将接触一个具体而强大的 IR——LLVM IR。LLVM 的 IR 是现代编译器工业中最成功的 IR 设计之一，它将三地址码和 SSA 形式有机地结合在一起，并提供了丰富的类型系统和指令集。学完下一章后，你将能够读懂和编写 .ll 格式的 LLVM IR 文件，并用 LLVM 工具链进行实际的编译实验。敬请期待。
